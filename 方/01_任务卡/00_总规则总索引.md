> **Canvas 看故事怎么长，卡看当前方案和最终交付，Base 看做到哪一步，项目管理看下一步做什么；正式内容只认 `02_描述词`。**

## 2. 三张工作台怎么分

### A. 主发散树 Canvas｜创作结构

- 结构：项目根 → 幕 → 正式卡 → 发散/探索关系。
- 每张正式卡在主树只保留一个主节点。
- 节点最多放四类入口：正式描述词、探索、素材、声音。
- 节点可以显示简短状态，但不展开“卡 → 执行索引 → FZM 执行卡”等数据库层级。
- 不自动重排、不自动删节点、不用旧文件覆盖用户在 Canvas 上的最新改动。
- 用户在 Canvas 的文字、颜色、位置、连线、改名和锁定标记是最高优先级。

### B. 卡 Canvas / 卡 MD｜当前方案与交付

每张卡的工作顺序固定为左到右：

`① 画面描述词 → ② 当前画面 → ③ 分镜时间描述词 → ④ 视频 → ⑤ 音效/配音`

- 卡 Canvas：放当前有效方案、短问题、短解决思路、各阶段入口，以及最终图片/视频的可点击链接。
- 卡 MD：保存正式描述词、分镜长文字和最终结果；不把探索过程堆进正式结果。
- 需要改描述词时，卡 Canvas 记录“改哪里、为什么”；卡 MD 只保留改后的结果。
- 阶段完成的旧过程不继续堆在卡上；需要回看时从对应幕 Canvas 或归档入口进入。
- 一张卡有 A/B/C 等子镜时，子镜单独登记、单独确认、单独锁定；总卡不能用一个状态掩盖未完成子镜。

### C. Base｜项目状态与筛选

- `方志敏_项目状态.base`：资产仓库，查图像 MD、当前画面、首尾帧、角色参考、分镜 MD、视频、音效和视频资产。
- `方志敏_项目状态_base1.base`：阶段确认表，查每张卡当前处于哪个阶段、缺什么、锁定与否；并单独查幕级声音。
- Base 只登记链接、状态和管理字段，不复制正式描述词正文。
- “缺什么”是建立下一批人工工单的主要依据。

## 3. 阶段确认规则

### 卡级五阶段｜只能选一个

每张卡的当前阶段只选一个数字，不同时勾选多列：

1. `画面描述词`
2. `当前画面`
3. `分镜时间描述词`
4. `视频`
5. `音效/配音`

> 阶段完成的确认表只展示“当前阶段”和“缺什么”；描述词参考表可以保留，作为对照，不把已完成 MD 重复堆到确认表里。

### 幕级两项｜可分别勾选

每幕在声音区独立确认两项：

- `环境音`
- `氛围音`

声音 MD 还要记录持续时间、对应卡位置和对应描述词。卡级五阶段与幕级声音不是同一列，不互相覆盖。

## 4. 锁定与解锁

锁定粒度按“内容段/子镜”执行，顺序不可倒退：

1. 内容概括
2. 画面描述与画面/首帧
3. 分镜头时间
4. 音效与视频

- 卡的五阶段是管理视图；四段锁定规则是审核与冻结规则，两者不冲突。
- 未锁定才允许提出修改、换图或重做；已锁定卡不生成、不替换、不改描述词。
- 需要改已锁内容时，必须先由用户明确解锁并写明原因；从被修改段起重新审核，后续锁定失效。
- “候选”“待审核”“文件存在”都不等于“用户确认”。
- 不自动锁卡；锁卡必须有用户确认或明确的验收证据。

## 5. 描述词修改限制

- 正式内容真源永远是 `方/02_描述词/`。
- 原描述词不直接删除；需要纠错时先保留版本/备份，再在卡 Canvas 记录修改点。
- 每轮最多修改 3 处；每处记录：原文位置、原内容、改后内容、修改原因、日期。
- 画面描述词与分镜时间描述词分开维护，不能用一方替换另一方。
- 画面描述必须写清位置、朝向、景别、手与物品关系、坐/站姿、与前后帧接续。
- 用户在 Canvas 或卡 MD 手动写入的内容优先保留，修改前先检查版本和 Git diff。

## 6. 资产与视频登记规则

- 资产文件名或登记表必须明确：幕、卡号、子镜号/视频号、用途和状态。
- 视频资产登记要把“文件名/视频号”与“归属卡”分开写清楚；不能只写 `21a`、`22`、`23` 而不标卡号。
- 现有第二幕桌面视频的登记口径：`21a.mp4 → 2-1A`，`22.mp4 → 2-2`，`23.mp4 → 2-3`；2-1B、2-1C 若无对应视频，写“待补”，不猜挂。
- 图像 MD 要有生成图或明确的待补标记；分镜时间 MD 要有视频或明确的待生成标记。
- 需要首帧/尾帧生成视频时，挂对应图片；只需要角色图时保留角色卡链接。
- 桌面原始视频、用户确认图、锁定视频不移动、不覆盖、不因整理而删除；外部文件用绝对路径或 `file:///` 链接登记。

## 7. 5090 批次工单规则｜只登记，不自动执行

- 工单按批次编号：`001`、`002`、`003`……
- `001` 是**一张批次工单**，下面登记 28 个任务组，不是建立 28 张工单。
- “缺什么”决定任务内容；卡有 A/B/C 子镜时，在同一任务组下列子镜，不改变 28 个任务组的计数。
- 工单要写：任务组序号、幕、卡号/子镜、缺什么、已有资产、所需描述词/首尾帧/角色参考、预计生成时间、提交状态和完成证据。
- 视频时长不是 GPU 生成耗时；预计分钟在首次真实运行后再回填。
- 未经用户明确要求，不启动 watcher、SSH、AutoDL、H3、后台轮询或自动回写。
- 云端设备开机、登录、支付和提交仍由用户本人最终确认。

## 7.1 交付审核双入口

- 任务交付审核固定看两处：① `[[05_画布工作台/5090工单/001_方志敏_下一批28任务]]` 的任务行、已有视频、完成证据和提交状态；② [[方志敏任务卡发散树]] 对应卡节点的当前内容、卡号和可点击的 `锁定视频`。
- 主发散树节点必须回显已经锁定的视频入口；视频仍可保留在桌面或素材库，节点通过绝对 `file:///` 链接或 Vault 视频链接打开。
- 只有工单有交付证据、且主发散树对应卡节点能点开锁定视频，才标记为“已交付”；阶段确认表只用于查看阶段/缺什么，不替代这两处交付核验。
- 锁定视频只能挂到实际卡号对应的节点，不能把 2-1A/B/C、4-5C/D 等不同子镜合并成无卡号的总视频。

## 8. 探索与回收

- 探索卡用于提出可验证问题、十元配比、多个方案和评分；不直接当正式结果。
- 方案采纳后，把最终结论写入 `02_描述词`，在卡 Canvas 标记当前有效方案。
- 已解决的问题和过程可回收到对应幕 Canvas；未解决问题继续留在卡 Canvas 的“待解决”区。
- 探索卡未拍板前不删除；拍板且结论已同步后，按旧版/归档规则保留可追溯副本。

## 9. 每次整理/提交的固定流程

1. 先读当前主 Canvas，核对幕、卡号、颜色、位置、链接和锁定标记。
2. 检查卡级 Base 的“当前阶段”和“缺什么”。
3. 只处理未锁定且确实缺失的内容；锁定内容跳过。
4. 把长描述词留在 `02_描述词`，把图片/视频/角色/声音链接登记到资产仓库。
5. 把短问题和短解决思路放卡 Canvas；需要回收的过程放幕 Canvas。
6. 根据“缺什么”整理 5090 批次工单；一个批次号下保持任务组计数清楚。
7. 写完后验证链接、Base YAML、文件存在性和 Git diff。
8. 报告“已处理、待用户确认、已跳过锁定、下一步”，不把计划说成已完成。

## 11. 当前状态快照

- 主剧情结构：当前主发散树已整理到第五幕；不要根据旧“ 三幕/16卡 ”描述覆盖当前结构。
- 声音确认：单独按六幕管理环境音和氛围音；以阶段确认表和声音状态 MD 为准。
- 批次工单：`001` 为一张 28 任务组批次工单。
- 自研执行系统：已停止并归档；不再使用 Meta Bind → watcher → Codex → H3 自动执行链路。
- 当前原则：普通 Obsidian + Canvas + Bases + Markdown + 人工提交；GitHub 现成 Skill/插件只在先验证后使用，不为缺功能自行开发。

## 12. 冲突处理优先级

1. 用户当前明确指令与 Canvas 最后修改
2. 锁定状态与用户确认记录
3. 本总规则总索引
4. `01_任务卡` 详细规则与模板
5. 正式 `02_描述词` 文件
6. 旧 Canvas、旧探索卡、旧工单和归档备份

> 任何发现冲突时，不猜、不覆盖；先报告冲突位置，再按最高优先级处理。
