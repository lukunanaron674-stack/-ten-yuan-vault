## 最重要经验

1. 先稳流程，再扩能力。F12 的价值来自稳定的“载入任务 - 自动执行 - 归档 - 停止”，不是一次塞进所有功能。
2. tabId 只能当临时会话标识。重启 Edge、刷新页面、重启电脑后，必须重新看 `multi-status`。
3. 中文路径和中文文件名容易让终端/脚本出现编码问题。给 F12 载入任务时，优先使用 `local-bridge` 目录里的 ASCII 文件名。
4. 自动跑之前必须确认任务数。看到 `R1/1` 时，通常是任务没有被正确拆分，不要继续自动跑。
5. 归档比继续跑更重要。只要产出有价值，先 `multi-archive`，再决定是否继续。
6. F12 不应该自动删除、自动覆盖、自动重写仓库核心文件。它负责采集与归档，真正的整理和上传由 Codex 接管。
7. 低智能模式适合 F12 控制、状态检查、跑命令；中智能适合总结和归档；高智能留给理论重构、删减规则和大脑架构。

## 本轮形成的操作判断

- 如果用户说“省 token”，Codex 应优先使用 F12 跑 ChatGPT，而不是自己长篇生成。
- 如果用户说“归档”，必须确认已经写入 Obsidian 文件，而不是只看浏览器内容。
- 如果用户说“继续”，先检查当前状态，不要盲目开新批。
- 如果用户说“跑完这次就结束”，完成当前批次后必须停止，不要续开下一批。
- 如果 token 快用完，优先停机、归档、写交接，不强求把自动链跑满。

## 已知风险

1. 多页 Agent 心跳会变 stale，`offline` 不一定代表页面关闭，但不应继续强推。
2. 自动归档可能抓到中间轮次，不一定是最终答案；关键批次结束后仍建议手动 `multi-archive`。
3. ChatGPT 回复完成检测仍可能误判，需要靠间隔和状态确认降低风险。
4. 浏览器页面刷新后，旧 tabId 可能失效。
5. 当前总控仍需要人工确认 GitHub/Obsidian 的最终提交，不要让 F12 直接写远端仓库。

## 下一步建议

1. 把 F12 的默认流程固定成三步：`multi-status`、`multi-auto`、`multi-archive`。
2. 建一个“归档轮次优先模式”：只保存 R4/R6/R12 等收束轮，降低噪音。
3. 加一个“归档质量标记”：final / mid / stale / manual。
4. 让 F12 输出更短的 CarryPacket，给 Codex 做二次吸收。
5. 把“Codex 大脑库”分成：训练素材、归档输出、可吸收规则、待删减清单、交接指南。
