# xz ↔ nz 水轴待审议｜《红楼梦》宝黛后期“同关系标签≠同对象层”护栏

## 0｜current canonical

只服从 latest L1 v1.6：

```text
水＝阳水 xz ↔ 阴水 nz
主题领域＝命运
广义变量＝可逆性与对象特异回返空间
xz：持续收窄
nz：保存、恢复或重建
```

本文件为 L4 边界研究，不修改 L1/L2、信息卡、准度卡、关系卡。木轴/火轴只迁移验证方法，不迁移理论结论。

## 1｜本轮唯一研究问题

> 《红楼梦》宝黛后期能否作为“同人物 + 同 current window + same object layer，xz=true 且 nz=true”的第一份四大名著共现样本？

结论：**不能 evidence-lock 为 same-layer co-occurrence。** 它是高价值 deferred guard：自然语言都可说“宝黛关系”，但实际被测 changed_variable 已经分裂。

## 2｜剧情事实

### trigger

第九十六回，贾母、王夫人、凤姐等决定尽快给宝玉办婚事，并形成“掉包”方案：对宝玉只说娶林姑娘，实际由宝钗成婚；同时要求消息不得外泄。黛玉后来从傻大姐处得知宝玉将娶宝钗，受到强烈冲击，仍去见宝玉。

第九十七回继续执行婚礼与隐瞒安排；黛玉的现实处境快速恶化。第九十八回宝玉得知黛玉已死，原双方现实关系无法再发生 bilateral reentry。

### actor

贾宝玉 ↔ 林黛玉；但婚配路径的主要处置主体另有贾母、王夫人、凤姐等家族决策者。

### action

- 家族层：决定宝玉婚配对象、压缩信息、实施掉包并推进婚礼；
- 宝黛层：黛玉获知消息后仍现实去见宝玉，但二人都处于失序状态，未完成可验证的冲突修复；随后黛玉死亡。

### object / object_layer 拆分

表面都叫“宝黛关系”，但至少拆成：

1. **婚配处置路径层**：宝玉最终与谁完成婚姻、哪些婚配路线仍现实可行；
2. **双方关系回返层**：宝玉↔黛玉是否仍存在自由、现实、双方可调用的 reentry / repair 资格。

### changed_variable

婚配处置层：

```text
多种婚配可能/讨论
→ 家族决定宝钗
→ 隐瞒与掉包方案形成
→ 婚礼执行
→ 宝黛婚配路线现实关闭
```

关系回返层：

```text
此前已有真实关系与修复史
→ 黛玉获知婚配消息
→ 现实去见宝玉
→ 双方失序，未形成稳定 bilateral repair
→ 黛玉死亡
→ 原双方现实 reentry 归零
```

## 3｜xz 独立判断

婚配处置路径具有明显 `xz` 候选骨架：未来婚配终点提前被家族决定，信息与现实行动围绕该终点排列，宝黛婚配的替代空间持续减少并最终关闭。

但这一 `xz` 的主体归因与对象层必须写成：

> **宝玉婚配处置路径 / 家族推进的婚姻结果空间**

不能写成“宝玉↔黛玉关系本身整体 xz”，否则把婚姻制度处置、双方关系回返与人物情绪混成一个对象层。

本文件不新增 pure-xz 计数；现有《三国演义》关羽麦城已提供更干净的 pure-xz 正控。

## 4｜nz 独立判断

宝黛在第二十九至三十回已经有一份 evidence-locked 的 repair-type pure `nz` 正控，证明历史上该对象特异关系曾具有 bilateral reentry + repair。

但**第九十六至九十八回 current window 不能把历史 nz 自动延续为 current stable nz**：

- 黛玉去见宝玉，证明 direct contact 尚未完全物理消失；
- 但双方当时均处于失序状态，文本不足以锁定一次新的双向修复成功；
- 随后黛玉死亡，原对象本人现实回返、回应与修复能力终止。

因此：

```text
historical_nz = verified in ch29-30
current_window_nz = not sufficient for evidence-lock as stable positive
```

## 5｜same current window / same object layer 压力测试

```text
same_characters = true
same_broad_relation_label = true
same_current_window = true
same_changed_variable = false / unresolved
same_object_layer = false at strict audit resolution
```

核心护栏：

> **“都发生在宝黛关系上”不等于 same object layer。**

婚配处置路径测试“谁拥有现实婚配终点、替代婚配路线是否被关闭”；`nz` 测试“双方是否仍有对象特异、自由、现实可调用的回返与修复资格”。两者可以在自然语言上共用“关系”标签，却不是同一个 changed_variable。

## 6｜nearest-neighbor

- `z`：家族做出婚配决定、婚礼节点属于强邻居；只有这些节点持续压缩多条未来路径时才支持 xz。
- `x`：家族对婚配安排、信息与执行具有处置/控制成分；这能解释大量现实变化，必须与 xz 分账。
- `xn`：掉包、保密、过礼、成婚流程具有组织与节点网络；流程本身不自动等于 xz。
- `nz`：不能用“宝黛感情一直很深”代替 current bilateral reentry / repair reality-test。

## 7｜removal test

### 拿掉历史 nz

若删除第二十九至三十回的既往修复事实，第九十六至九十八回仍能形成婚配路径收窄候选；说明该 xz 不依赖 current nz 成立。

### 拿掉婚配处置 xz

若家族没有推进宝钗婚礼、宝黛关系仍可能保留此前验证过的回返/修复能力；说明历史 nz 也不依赖婚配路径 xz 成立。

因此不能由共现外观推 strict。

## 8｜reverse test

若反向改写为：

- 家族取消掉包并公开信息；
- 宝玉婚配存在多个现实可行选项；
- 宝黛婚配路线未被制度性关闭；

则婚配路径 xz 应下降，但这不会自动决定宝黛双方是否愿意重接。

反之，若宝黛双方明确永久拒绝彼此 reentry，nz 应下降，也不会自动决定家族是否仍推进宝钗婚礼。

## 9｜third-factor freeze

需要冻结：

- 贾母/王夫人/凤姐的婚配处置权；
- 掉包和信息不对称；
- 宝玉病情与黛玉病情；
- “金玉良缘”主题词；
- 悲剧结局与读者预知。

这些因素都能制造强烈“命定爱情悲剧”观感，却不能替代 same-object-layer 与两端独立 reality-test。

## 11｜本轮锁定的边界

> **same characters + same current window + same natural-language relationship label ≠ same object layer。**

必须继续拆到：

```text
actor
+ object
+ changed_variable
+ reality anchor
```

若一端测试的是“婚配处置路径是否被压缩”，另一端测试的是“双方关系是否仍可现实回返并修复”，就不能把“都是宝黛关系”当作 strict 水轴同层证据。

本轮不提高 pure/co-occurrence/dynamic/strict 的 evidence-locked 统计，只新增 1 条 deferred false-same-layer guard。下一轮最高价值缺口仍是：四大名著内真正 **same actor / same current window / same object / same changed_variable** 的 `xz=true + nz=true` 共现，再进行 removal / reverse 判断是否 non-strict 或 strict。
