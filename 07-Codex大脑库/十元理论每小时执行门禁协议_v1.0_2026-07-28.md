# 十元理论每小时执行门禁协议 v1.1

> 本协议只治理任务是否真实启动、真实写入、真实核验以及如何防止重复空跑；不改写十元关系定义。理论断点仍由《每次任务必读_十元关系防遗忘清单》管理。文件名保留 v1.0 是为了稳定既有入口，正文版本以 frontmatter 为准。

## 1. 执行模式与状态码

每轮必须先判定执行模式：

```text
real_git_access
＝已真实读取仓库、具备目标分支写权限，并能重新读取提交与文件

simulation_only
＝只能推理或生成候选文本，不能真实写入仓库
```

允许状态码：

| 状态 | 含义 | 是否可写理论结论 | 是否可写“提交成功” |
|---|---|---:|---:|
| `READY` | 尚未占用本小时槽位 | 否 | 否 |
| `RUNNING_REAL` | 真实 Git 读写链已验证 | 是，仍须过理论门槛 | 否，直到回读成功 |
| `AWAITING_LEDGER_VERIFY` | 第一提交完成，等待唯一账本第二提交与回读 | 否，不得提前宣告整轮完成 | 否 |
| `BLOCKED_NO_REPO_ACCESS` | 无法读取仓库或 main | 否 | 否 |
| `BLOCKED_NO_REPO_WRITE` | 能读但无写权限 | 否 | 否 |
| `BLOCKED_ATOMIC_WRITE_UNAVAILABLE` | 多文件第一提交无法原子完成 | 否 | 否 |
| `BLOCKED_REQUIRED_FILE_MISSING` | 强制文件缺失 | 否 | 否 |
| `IDEMPOTENT_SKIP` | 同一调度槽位已完成或已有有效运行 | 否，不重复审计 | 否，不制造提交 |
| `CONCURRENT_RESTART_REQUIRED` | 目标文件在本轮中被并发修改 | 否，须从最新断点重启 | 否 |
| `INCOMPLETE_AUDIT` | 独立审计未完成 | 否 | 仅可提交失败状态，不能写理论成功 |
| `BLOCKED_WAITING_EVIDENCE` | 连续三轮没有新增独立证据 | 否，关系暂时退出轮转 | 否 |
| `VERIFIED_SUCCESS` | 第二提交与最终回读全部真实存在 | 是 | 是，仅以唯一运行账本为最终依据 |

## 2. 启动门禁

在理论判断之前必须完成：

```text
读取 main 最新 SHA
→ 读取强制必读中枢
→ 读取本协议
→ 核验仓库、默认分支、读权限与写权限
→ 核验外部每小时调度器处于启用状态
→ 生成 slot_id 与 attempt_id
→ 检查唯一账本中是否已有同一 slot_id 的有效运行
→ 才进入理论强制读取顺序
```

本文件不会自己触发任务。每小时运行依赖外部调度器；调度器停用时，仓库文件即使写着“每小时”也不会自行执行。

## 3. 稳定槽位、尝试 ID 与幂等

不得再把会被无关提交改变的 main SHA 放进唯一槽位键。统一拆成：

```text
slot_id
= scheduler_task_id | YYYY-MM-DD-HH | next_priority_relation

attempt_id
= slot_id | starting_main_sha | retry_sequence
```

规则：

1. `slot_id` 表示一个计划小时里对一条关系的唯一工作槽；同一槽位只允许一个最终有效结果。
2. `attempt_id` 只记录并发环境与重试，不负责幂等判定。
3. 唯一账本已存在相同 `slot_id` 且状态为 `VERIFIED_SUCCESS` 时，直接记为 `IDEMPOTENT_SKIP`，不得再次扩写证据或制造提交。
4. 同一槽位已有 `RUNNING_REAL` 或 `AWAITING_LEDGER_VERIFY` 的较新尝试时，旧尝试停止；不得因为无关任务改变 main SHA 就生成第二个合法槽位。
5. 补跑沿用原 `slot_id`，递增 `retry_sequence` 并写明补跑原因；只有明确的人工补充轮才允许建立带 `manual-supplement` 后缀的新槽位。

## 4. 双状态与最终成功权威

强制必读中枢和唯一运行账本承担不同职责：

```text
强制必读中枢
= 保存上一轮已验证结果、当前理论断点、当前槽位的进行中状态

唯一运行账本
= 保存本轮最终状态；只有第二提交后回读成功，才可写 VERIFIED_SUCCESS
```

中枢必须使用：

```yaml
last_verified_run_id: 上一轮已经在唯一账本完成最终核验的 attempt_id 或 null
last_legacy_run_id: 新门禁启用前的最后运行，仅作历史引用
current_slot_id: 本轮 slot_id 或 null
current_attempt_id: 本轮 attempt_id 或 null
current_run_status: READY | RUNNING_REAL | AWAITING_LEDGER_VERIFY | 失败状态
```

禁止在第一提交中把本轮写成 `VERIFIED_SUCCESS`。第一提交完成时，中枢最多写 `AWAITING_LEDGER_VERIFY`；第二提交和最终回读不再反向改写第一提交中的状态。整轮是否成功只查询唯一运行账本的最新同槽位记录。

## 5. 并发、短租约与原子第一提交

本协议不依赖虚构的永久文件锁，使用“最新 SHA + 目标 blob SHA”形成短租约：

1. 启动时记录 `starting_main_sha`。
2. 写入前重新读取所有目标文件 blob SHA 与最新 main SHA。
3. 若 main 变化但目标 blob 未变，可记录并发来源后继续。
4. 若任一目标 blob 已变，状态改为 `CONCURRENT_RESTART_REQUIRED`；不得以旧内容覆盖新内容。
5. 第一提交若只修改一个文件，可使用 Contents API 的单文件提交。
6. 第一提交若修改两个或以上文件，必须使用 Git Data 原子链：`create_blob → create_tree(base_tree) → create_commit(parent=current_main) → update_ref(force=false)`；所有目标文件必须落在同一个 commit 中。
7. 工具不具备上述原子链时，不得把多次单文件提交冒充“第一提交”；应标记 `BLOCKED_ATOMIC_WRITE_UNAVAILABLE`，或把本轮收窄到只回写中枢且不修改理论正本。
8. 第一提交后必须重新读取 commit 与全部目标文件。
9. 第二提交前再次读取唯一账本最新 blob SHA。
10. 第二提交后再次读取 commit、账本版本、slot_id、attempt_id 与下一断点。

## 6. 增量预检与单轮阶段

每个小时仍只处理一条关系，但不是每轮都机械重跑整篇审计。先做证据增量预检：

```text
P0 执行预检与 slot_id 幂等
→ P0.5 新增独立证据 / 新正本冲突预检
```

若没有新增独立证据且没有新的实质冲突：

```text
轻量轮
→ 核对旧缺口仍成立
→ consecutive_no_new_evidence + 1
→ 只回写中枢状态与唯一账本
→ 不重新扩写正反例、专项正本或完整审计
```

若出现新增独立证据或新冲突，才进入完整轮：

```text
P1 端点、变量与候选机制
→ P2 正反例、最近邻、拿掉、反向与三元/十元核验
→ P3 95%门槛、正本写入或证据缺口回写
→ P4 第一提交、唯一账本第二提交与回读验证
```

任一必要阶段未完成，状态为 `INCOMPLETE_AUDIT`。不得为了赶整点补造案例、置信度或理论结论。

## 7. 置信度门槛与评分刻度

每轮完整审计至少分别记录：

- 端点稳定度；
- 机制清晰度；
- 独立证据强度；
- 竞争解释排除度；
- 拿掉与反向可逆性；
- 跨案例复现度。

最终置信度按最弱环节计算：

```text
final_confidence = min(
  endpoint,
  mechanism,
  independent_evidence,
  rival_exclusion,
  reversibility,
  replication
)
```

统一刻度：

| 分数 | 最低证据状态 |
|---|---|
| `95–100` | 至少两组独立纯例通过全部关键控制；端点与目标变量稳定；无仍可解释主要变化的竞争机制；拿掉与反向测试均通过；跨不同人物或情境复现 |
| `90–94` | 方向与机制基本稳定，但仍有一个关键控制、一个边界或一个竞争解释未完全排除 |
| `80–89` | 方向可信，但样本混有第三因素、授权残留、共享先验、状态变化或前置变量，尚不能锁定严格机制 |
| `60–79` | 主要是共现、先后、表达强度、进入概率、视觉相似或场景效果 |
| `<60` | 关系方向、端点或被改变变量本身不稳定 |

强制封顶规则：

- 任一端点仍有稳定本体/当前状态混淆，`endpoint ≤ 89`；
- 没有至少一个通过关键控制的纯例，`independent_evidence ≤ 79`；
- 仍有一个能解释主要变化的竞争机制，`rival_exclusion ≤ 89`；
- 拿掉源端点后变化仍同样发生，或反向不恢复，`reversibility ≤ 79`；
- 只在单一人物、单一制度或同一文化模板中成立，`replication ≤ 89`。

只有六项都不低于95%，且不存在超过5%的定义分歧，才允许锁定严格机制。平均分不得掩盖某一项证据断裂。

## 8. 每关系独立尝试状态

不得只保存当前关系的一个临时计数。所有未锁定关系必须在中枢维护长期映射：

```yaml
relation_attempt_states:
  "关系名":
    total_attempts_since_gate_v1_1: 0
    consecutive_no_new_evidence: 0
    last_novel_evidence: null
    last_slot_id: null
    status: ready
```

新增独立证据必须满足至少一项：

- 新的纯案例通过旧轮未通过的控制条件；
- 新反例推翻或明显收窄候选机制；
- 新材料完成关键第三因素隔离；
- 用户解决了真实定义分歧；
- 正本、词典或专项出现新的实质冲突。

连续三轮没有新增独立证据时：

```text
status = blocked_waiting_evidence
→ 保留最新缺口与证据目标
→ 轮转到下一条关系
→ 不再重复扩写同一审计
```

只有出现上述新证据标记后才能重新进入推进池。

## 9. 案例与关系隔离

案例证据必须按以下链条写入：

```text
原始事实
→ 对象层归属
→ 人物与阶段
→ 行为功能
→ 具体源端点与目标端点
→ 目标变量变化
→ 生克补候选
```

案例不能因为“像某关系”就反向定义关系；名作光环、视觉对照、剧情先后和角色标签不能作为关系端点。

## 10. 已锁定关系冻结

已锁定关系至少冻结：

- 源端点；
- 目标端点；
- 核心机制；
- 被改变变量；
- 成立阶段；
- 关键红线；
- 锁定范围是窄机制还是整条关系。

修改已锁定内容时，不得直接覆盖。必须新建或更新 `canonical-amendment`，写明 `covers / conflicts-with / supersedes` 的准确范围，并通过同等级证据审计。

## 11. 必读中枢与账本字段

每轮必须在强制必读中枢维护：

```yaml
execution_protocol_version: v1.1
scheduler_task_id: 6a57edfc813081918542846f23358130
execution_mode: real_git_access
last_verified_run_id: ...
last_legacy_run_id: ...
current_slot_id: ...
current_attempt_id: ...
current_run_status: ...
max_consecutive_no_new_evidence: 3
```

唯一运行账本额外记录：

- `slot_id` 与 `attempt_id`；
- 本轮是轻量轮还是完整轮；
- 本轮六项置信度与每项评分依据；
- 是否产生新增独立证据；
- 本关系连续无新证据次数；
- 幂等检查结果；
- 并发检查结果；
- 第一提交是否为原子提交及其文件列表；
- 调度器 ID 与执行模式；
- 失败状态码；
- 第二提交后最终状态。

## 12. 禁止虚假闭环

以下任一项缺失，禁止写“提交成功”：

- 真实第一提交 SHA；
- 第一提交后重新读取 commit 与全部目标文件；
- 必读中枢只能记录进行中状态，未提前冒充本轮最终成功；
- 唯一账本包含本轮 `slot_id` 与 `attempt_id`；
- 真实第二提交 SHA；
- 第二提交后再次回读成功；
- 唯一账本最终状态明确为 `VERIFIED_SUCCESS`。

只完成推理、草稿、补丁文本或模拟 SHA 时，必须明确标记 `simulation_only`，不能冒充仓库已修改。

## 13. 一句话

```text
先证明这轮真的运行，再证明关系真的成立；最终成功只由账本回读确认。
```
