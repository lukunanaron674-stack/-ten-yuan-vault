# 十元理论每小时执行门禁协议 v1.0

> 本协议只治理任务是否真实启动、真实写入、真实核验以及如何防止重复空跑；不改写十元关系定义。理论断点仍由《每次任务必读_十元关系防遗忘清单》管理。

## 1. 执行模式与状态码

每轮必须先判定执行模式：

```text
real_git_access
＝已真实读取仓库、具备目标分支写权限，并能重新读取提交与文件

simulation_only
＝只能推理或生成候选文本，不能真实写入仓库
```

允许状态码：

| 状态 | 含义 | 是否可写理论结论 | 是否可写“提交成功” |
|---|---|---:|---:|
| `RUNNING_REAL` | 真实 Git 读写链已验证 | 是，仍须过理论门槛 | 否，直到回读成功 |
| `BLOCKED_NO_REPO_ACCESS` | 无法读取仓库或 main | 否 | 否 |
| `BLOCKED_NO_REPO_WRITE` | 能读但无写权限 | 否 | 否 |
| `BLOCKED_REQUIRED_FILE_MISSING` | 强制文件缺失 | 否 | 否 |
| `IDEMPOTENT_SKIP` | 同一运行 ID 已完成 | 否，不重复审计 | 否，不制造提交 |
| `CONCURRENT_RESTART_REQUIRED` | 目标文件在本轮中被并发修改 | 否，须从最新断点重启 | 否 |
| `INCOMPLETE_AUDIT` | 独立审计未完成 | 否 | 仅可提交失败状态，不能写理论成功 |
| `BLOCKED_WAITING_EVIDENCE` | 连续三轮没有新增独立证据 | 否，关系暂时退出轮转 | 否 |
| `VERIFIED_SUCCESS` | 两次提交及回读全部真实存在 | 是 | 是 |

## 2. 启动门禁

在理论判断之前必须完成：

```text
读取 main 最新 SHA
→ 读取强制必读中枢
→ 读取本协议
→ 核验仓库、默认分支、读权限与写权限
→ 核验外部每小时调度器处于启用状态
→ 生成本轮 run_id
→ 检查唯一账本中是否已有同一 run_id
→ 才进入理论强制读取顺序
```

本文件不会自己触发任务。每小时运行依赖外部调度器；调度器停用时，仓库文件即使写着“每小时”也不会自行执行。

## 3. 运行 ID 与幂等

统一运行 ID：

```text
YYYY-MM-DD-HH | next_priority_relation | starting_main_sha
```

规则：

1. 同一小时、同一关系、同一起始 SHA 只允许完成一次。
2. 唯一账本已存在相同 `run_id` 且状态为 `VERIFIED_SUCCESS` 时，直接记为 `IDEMPOTENT_SKIP`，不得再次扩写证据或制造提交。
3. 同一小时由不同起始 SHA 触发时，保留较新的 main；旧运行必须停止。
4. 补跑必须使用新的明确 `run_id`，并写明补跑原因，不能伪装成原轮首次运行。

## 4. 并发与写入租约

本协议不依赖虚构的永久文件锁，使用“最新 SHA + 目标 blob SHA”形成短租约：

1. 启动时记录 `starting_main_sha`。
2. 写入前重新读取所有目标文件 blob SHA 与最新 main SHA。
3. 若 main 变化但目标 blob 未变，可记录并发来源后继续。
4. 若任一目标 blob 已变，状态改为 `CONCURRENT_RESTART_REQUIRED`；不得以旧内容覆盖新内容。
5. 第一提交后必须重新读取 commit 与目标文件。
6. 第二提交前再次读取唯一账本最新 blob SHA。
7. 第二提交后再次读取 commit、账本版本、运行 ID 与下一断点。

## 5. 单轮内部阶段

每个小时仍只审计一条关系，但内部必须依次经过五阶段：

```text
P0 执行预检
→ P1 端点、变量与候选机制
→ P2 正反例、最近邻、拿掉、反向与三元/十元核验
→ P3 95%门槛、正本写入或证据缺口回写
→ P4 两次提交与回读验证
```

任一阶段未完成，状态为 `INCOMPLETE_AUDIT`。不得为了赶整点补造案例、置信度或理论结论。

## 6. 置信度门槛

95%不是单一主观数字。每轮至少分别记录：

- 端点稳定度；
- 机制清晰度；
- 独立证据强度；
- 竞争解释排除度；
- 拿掉与反向可逆性；
- 跨案例复现度。

最终置信度按最弱环节计算：

```text
final_confidence = min(
  endpoint,
  mechanism,
  independent_evidence,
  rival_exclusion,
  reversibility,
  replication
)
```

只有六项都不低于95%，且不存在超过5%的定义分歧，才允许锁定严格机制。平均分不得掩盖某一项证据断裂。

## 7. 防重复空跑

每条未锁定关系必须维护：

```yaml
attempt_state:
  total_attempts_since_gate_v1: 0
  consecutive_no_new_evidence: 0
  last_novel_evidence: null
  status: ready
```

新增独立证据必须满足至少一项：

- 新的纯案例通过旧轮未通过的控制条件；
- 新反例推翻或明显收窄候选机制；
- 新材料完成关键第三因素隔离；
- 用户解决了真实定义分歧；
- 正本、词典或专项出现新的实质冲突。

连续三轮没有新增独立证据时：

```text
status = blocked_waiting_evidence
→ 保留最新缺口与证据目标
→ 轮转到下一条关系
→ 不再重复扩写同一审计
```

只有出现上述新证据标记后才能重新进入推进池。

## 8. 案例与关系隔离

案例证据必须按以下链条写入：

```text
原始事实
→ 对象层归属
→ 人物与阶段
→ 行为功能
→ 具体源端点与目标端点
→ 目标变量变化
→ 生克补候选
```

案例不能因为“像某关系”就反向定义关系；名作光环、视觉对照、剧情先后和角色标签不能作为关系端点。

## 9. 已锁定关系冻结

已锁定关系至少冻结：

- 源端点；
- 目标端点；
- 核心机制；
- 被改变变量；
- 成立阶段；
- 关键红线；
- 锁定范围是窄机制还是整条关系。

修改已锁定内容时，不得直接覆盖。必须新建或更新 `canonical-amendment`，写明 `covers / conflicts-with / supersedes` 的准确范围，并通过同等级证据审计。

## 10. 必读中枢与账本字段

每轮必须在强制必读中枢维护：

```yaml
execution_protocol_version: v1.0
scheduler_task_id: 6a57edfc813081918542846f23358130
execution_mode: real_git_access
last_run_id: ...
execution_status: ...
active_relation_attempts: ...
consecutive_no_new_evidence: ...
max_consecutive_no_new_evidence: 3
```

唯一运行账本额外记录：

- 本轮六项置信度；
- 是否产生新增独立证据；
- 本关系连续无新证据次数；
- 幂等检查结果；
- 并发检查结果；
- 调度器 ID 与执行模式；
- 失败状态码。

## 11. 禁止虚假闭环

以下任一项缺失，禁止写“提交成功”：

- 真实 commit SHA；
- 提交后重新读取 commit；
- 目标文件内容真实存在；
- 必读中枢版本已更新；
- 唯一账本包含本轮运行 ID；
- 第二提交后再次回读成功。

只完成推理、草稿、补丁文本或模拟 SHA 时，必须明确标记 `simulation_only`，不能冒充仓库已修改。

## 12. 一句话

```text
先证明这轮真的运行，再证明关系真的成立。
```
