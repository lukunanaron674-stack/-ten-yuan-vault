# 十元理论每小时执行门禁协议 v1.2

> 本协议只治理任务是否真实启动、真实读取现行卡体系、真实写入、真实核验以及如何防止重复空跑；不直接改写十元关系定义。理论断点仍由《每次任务必读_十元关系防遗忘清单》管理。文件名保留 v1.0 是为了稳定既有入口，正文版本以前言为准。

## 1. 执行模式与状态码

```text
real_git_access
= 已真实读取仓库、具备main写权限，并能回读提交与文件

simulation_only
= 只能推理或生成候选文本，不能真实写入仓库
```

| 状态 | 含义 | 可写理论结论 | 可写“提交成功” |
|---|---|---:|---:|
| `READY` | 尚未占用本小时槽位 | 否 | 否 |
| `RUNNING_REAL` | 真实Git读写链已验证 | 过理论门槛后可以 | 否 |
| `AWAITING_LEDGER_VERIFY` | 第一提交完成，等待账本第二提交与回读 | 否 | 否 |
| `BLOCKED_NO_REPO_ACCESS` | 无法读取仓库或main | 否 | 否 |
| `BLOCKED_NO_REPO_WRITE` | 能读但无写权限 | 否 | 否 |
| `BLOCKED_ATOMIC_WRITE_UNAVAILABLE` | 多文件第一提交无法原子完成 | 否 | 否 |
| `BLOCKED_REQUIRED_FILE_MISSING` | 强制文件缺失 | 否 | 否 |
| `IDEMPOTENT_SKIP` | 同槽位已完成或已有有效运行 | 否 | 否 |
| `CONCURRENT_RESTART_REQUIRED` | 目标文件被并发修改 | 否 | 否 |
| `INCOMPLETE_AUDIT` | 独立审计未完成 | 否 | 否 |
| `BLOCKED_WAITING_EVIDENCE` | 连续三轮无新增独立证据 | 否 | 否 |
| `VERIFIED_SUCCESS` | 第二提交与最终回读均存在 | 是 | 是，仅以唯一账本为准 |

## 2. 启动门禁与三层卡体系

理论判断前必须完成：

```text
读取main最新SHA
→ 读取强制必读中枢
→ 读取本协议
→ 核验仓库、默认分支、读写权限与外部调度器
→ 生成slot_id与attempt_id
→ 检查唯一账本幂等状态
→ 读取Codex大脑总入口
→ 读取十元信息卡正本总览
→ 读取本轮源、目标端点现行信息卡
→ 读取准度卡总控与源、目标准度卡
→ 读取生克补卡总控与本轮关系类型卡
→ 读取十元生补克表、关系专项索引、关系词典、待确认队列与唯一账本
→ 才能开始审计
```

三层职责：

```text
信息卡：端点是什么
准度卡：为何该对象必须判成该端点
生卡 / 克卡 / 补卡：两个已成立端点之间发生什么
```

三层不得互相替代。`01-十元系统/001-概念的定义.md`、`z切分焦点`、`x现象集合`只作`legacy-evidence-only`，不得生成、替代或证明现行端点。

本文件不会自己触发任务。每小时运行依赖外部调度器；调度器停用时，仓库文件不会自行执行。

## 3. 稳定槽位、尝试ID与幂等

```text
slot_id
= scheduler_task_id | YYYY-MM-DD-HH | next_priority_relation

attempt_id
= slot_id | starting_main_sha | retry_sequence
```

1. `slot_id`表示计划小时内对一条关系的唯一工作槽，同槽只允许一个最终有效结果。
2. `attempt_id`只记录并发与重试，不负责幂等。
3. 唯一账本已有同`slot_id`且`VERIFIED_SUCCESS`时，直接`IDEMPOTENT_SKIP`。
4. 同槽已有较新`RUNNING_REAL`或`AWAITING_LEDGER_VERIFY`时，旧尝试停止。
5. 补跑沿用原`slot_id`，递增`retry_sequence`并写明原因；只有明确人工补充轮可建立`manual-supplement`后缀。

## 4. 双状态与最终成功权威

```text
强制必读中枢
= 上一轮已验证结果 + 当前理论断点 + 当前槽位进行中状态

唯一运行账本
= 本轮最终状态；只有第二提交后回读成功才可写VERIFIED_SUCCESS
```

中枢字段：

```yaml
last_verified_run_id: 上一轮已在唯一账本完成最终核验的attempt_id或null
last_legacy_run_id: 新门禁启用前的最后运行，仅作历史引用
current_slot_id: 本轮slot_id或null
current_attempt_id: 本轮attempt_id或null
current_run_status: READY | RUNNING_REAL | AWAITING_LEDGER_VERIFY | 失败状态
```

第一提交不得写本轮`VERIFIED_SUCCESS`。若账本已成功而中枢残留`AWAITING_LEDGER_VERIFY`，必须以已回读账本为准并原位修正中枢。

## 5. 并发、短租约与原子第一提交

1. 启动时记录`starting_main_sha`。
2. 写入前重读所有目标blob SHA与最新main SHA。
3. main变化但目标blob未变，可记录并发来源后继续。
4. 任一目标blob变化，状态改为`CONCURRENT_RESTART_REQUIRED`，不得覆盖。
5. 第一提交只改一个文件，可用Contents API。
6. 第一提交修改两个或以上文件，必须使用Git Data原子链：`create_blob → create_tree(base_tree) → create_commit(parent=current_main) → update_ref(force=false)`。
7. 无原子链能力时标记`BLOCKED_ATOMIC_WRITE_UNAVAILABLE`，或收窄为只回写中枢且不改理论正本；不得连续单文件提交冒充原子第一提交。
8. 第一提交后回读commit与全部目标文件。
9. 第二提交前重读唯一账本blob SHA。
10. 第二提交后回读commit、账本版本、slot_id、attempt_id与下一断点。

## 6. 增量预检与单轮阶段

```text
P0 执行预检与幂等
→ P0.5 新增独立证据 / 新正本冲突预检
```

无新增且无实质冲突：

```text
轻量轮
→ 核对旧缺口仍成立
→ consecutive_no_new_evidence + 1
→ 只回写中枢状态与唯一账本
→ 不重复扩写正反例、专项或完整审计
```

有新增或新冲突：

```text
完整轮
P1 三层卡端点、变量与候选机制
→ P2 正反例、最近邻、拿掉、反向、第三因素与三元/十元核验
→ P3 七项95%门槛、正本写入或证据缺口回写
→ P4 第一提交、唯一账本第二提交与回读验证
```

任一必要阶段未完成，状态为`INCOMPLETE_AUDIT`。不得为了赶整点补造案例、分数或结论。

## 7. 七项置信度门槛与历史兼容

每轮新审计必须分别记录：

- `source_endpoint`：源端点稳定度；
- `target_endpoint`：目标端点稳定度；
- `mechanism`：机制清晰度；
- `independent_evidence`：独立证据强度；
- `rival_exclusion`：竞争解释排除度；
- `reversibility`：拿掉与反向可逆性；
- `replication`：跨案例复现度。

```text
final_confidence = min(
  source_endpoint,
  target_endpoint,
  mechanism,
  independent_evidence,
  rival_exclusion,
  reversibility,
  replication
)
```

旧账本若只有聚合`endpoint`，保留为历史六项记录，不得事后伪造源、目标拆分值。新账本为了兼容旧读取器，可以同时写：

```text
endpoint = min(source_endpoint, target_endpoint)
```

但聚合字段不得替代七项主记录。

| 分数 | 最低证据状态 |
|---|---|
| `95–100` | 至少两组独立纯例通过全部关键控制；两端与目标变量稳定；无存活竞争机制；拿掉与反向通过；跨不同人物或情境复现 |
| `90–94` | 方向与机制基本稳定，但仍有一个关键控制、边界或竞争解释未排除 |
| `80–89` | 方向可信，但混有第三因素、授权残留、共享先验、状态变化或前置变量 |
| `60–79` | 主要是共现、先后、表达强度、进入概率、视觉相似或场景效果 |
| `<60` | 关系方向、端点或被改变变量不稳定 |

强制封顶：

- 源端点层级混淆，`source_endpoint ≤ 89`；
- 目标端点层级混淆，`target_endpoint ≤ 89`；
- 无通过关键控制的纯例，`independent_evidence ≤ 79`；
- 存活竞争机制仍解释主要变化，`rival_exclusion ≤ 89`；
- 拿掉后变化仍发生或反向不恢复，`reversibility ≤ 79`；
- 只在单一人物、制度或文化模板成立，`replication ≤ 89`。

只有七项全部不低于95%，且不存在超过5%的核心定义分歧，才允许锁定严格机制。平均分不得掩盖断裂。

## 8. 每关系独立尝试状态

所有未锁定关系必须长期维护：

```yaml
relation_attempt_states:
  "关系名":
    total_attempts_since_gate_v1_1: 0
    consecutive_no_new_evidence: 0
    last_novel_evidence: null
    last_slot_id: null
    status: ready
```

新增独立证据至少满足一项：

- 新纯例通过旧轮未通过的控制；
- 新反例推翻或明显收窄候选机制；
- 新材料完成关键第三因素隔离；
- 用户解决真实定义分歧；
- 信息卡、准度卡、关系卡、关系表、词典或专项出现新的实质冲突。

连续三轮无新增：

```text
status = BLOCKED_WAITING_EVIDENCE
→ 保留最新缺口与证据目标
→ 轮转下一关系
→ 不再重复扩写
```

只有出现有效新证据标记后才能重新进入推进池。

## 9. 案例与关系隔离

```text
原始事实
→ 对象层归属
→ 人物与阶段
→ 行为功能
→ 信息卡候选端点
→ 准度卡验证
→ 目标变量变化
→ 生克补卡候选
```

案例不能因“像某关系”反向定义关系；名作光环、视觉对照、剧情先后和角色标签不能作为端点。

## 10. 已锁定关系冻结

已锁定关系至少冻结：源端点、目标端点、核心机制、被改变变量、成立阶段、关键红线、锁定范围。修改时不得直接覆盖；必须新建或更新`canonical-amendment`，写明`covers / conflicts-with / supersedes`准确范围，并通过同等级证据审计。

## 11. 中枢与账本字段

中枢至少维护：

```yaml
execution_protocol_version: v1.2
information_card_index_version: v1.1
accuracy_card_index_version: v0.5
relation_card_index_version: v1.0
confidence_schema: seven-dimension-v1
scheduler_task_id: 6a57edfc813081918542846f23358130
execution_mode: real_git_access
last_verified_run_id: ...
last_legacy_run_id: ...
current_slot_id: ...
current_attempt_id: ...
current_run_status: ...
max_consecutive_no_new_evidence: 3
```

唯一运行账本额外记录：

- `slot_id`与`attempt_id`；
- 轻量轮或完整轮；
- 信息卡、准度卡、关系卡与关系表版本；
- 七项置信度、每项依据、最弱项，以及兼容`endpoint`字段；
- 是否产生新增独立证据；
- 本关系连续无新证据次数；
- 幂等与并发结果；
- 第一提交原子性、文件列表与SHA；
- 调度器ID、执行模式与失败状态码；
- 第二提交SHA与最终状态。

## 12. 禁止虚假闭环

以下任一项缺失，禁止写“提交成功”：

- 真实第一提交SHA；
- 第一提交后回读commit与全部目标文件；
- 中枢未提前冒充本轮最终成功；
- 唯一账本含本轮slot_id与attempt_id；
- 真实第二提交SHA；
- 第二提交后回读成功；
- 唯一账本最终状态明确为`VERIFIED_SUCCESS`。

只完成推理、草稿、补丁文本或模拟SHA时，必须标记`simulation_only`。

## 13. 一句话

```text
先证明端点经过现行卡体系，再证明关系成立；先证明这轮真的运行，最终成功只由账本回读确认。
```
