# 待审议｜旧严格补判据是否系统性过宽｜正本冲突暂停

## 0｜状态纠正

本文件原先提出一个更严的新门：

> 拿掉 `zx` 后，必须直接损伤 `nx` 自身的资源、许可、保护、专业能力等“核心功能”，否则只能算 `nx→zx` 单向补。

2026-08-26 重新读取仓库正本后发现：这个门**比当前 `zx补nx_补卡` 正本额外增加了条件，并与正本明文定义发生冲突**。

正本当前写的是：

```text
nx 补 zx：补入外部权限接口、救兵、关系通道与非正面解决方案。

zx 补 nx：把借到的资源、关系与通道重新转成实际行动、公开决定和结果推进，改变 nx 单独运行时“有路径却缺落地权能”的缺口。
```

红线只要求：

```text
拿掉任一端
→ 另一端仍成立但出现可命名缺口
→ 补回后缺口得到改善
```

正本**没有要求**：

```text
拿掉 zx
→ nx 自己的资源处分能力 / 许可能力 / 专业能力本体必须受损
```

因此本文件原先的“nx 自身核心功能损伤门”目前只能算候选新方法，不能在未修改正本的情况下反向生效。

## 1｜层级纪律

仓库层级必须保持：

```text
canonical-current 正本
>
pending-review / 方法卡 / 运行记录
```

所以：

- pending-review 可以提出“是否应该把严格补收得更窄”；
- 但在 `zx补nx_补卡` 未正式修改之前；
- 不得用这个更窄候选门撤销与正本文字直接相容的严格补案例；
- 更不得把“新门下统计为0”写成当前正本事实。

### 2.4 鸳鸯抗婚

按当前补卡重新复核：

```text
nx→zx：贾母真实保护/留用/否决接口，补鸳鸯个人拒绝缺稳定现实阻断力
zx→nx：鸳鸯公开占据并坚持拒绝方向，把贾母已有保护路径具体化、触发并兑现为“拒婚成功”的公开现实结果，补“有路径却缺落地权能”
```

原文内部反事实亦支持：邢夫人的思路正是“老太太虽不依，搁不住鸳鸯自己愿意”。若鸳鸯本人愿意，贾母的一般留用偏好并不会自动等价生成“替鸳鸯拒婚”的同一结果。

“贾母依赖鸳鸯”可以解释她为什么愿意动用保护接口，但不能替代鸳鸯自己的拒绝方向、贾母的真实否决能力以及两端对同一强纳瓶颈的双向补缺。

因此鸳鸯抗婚按 current canonical 恢复严格 `zx↔nx` 正例，事实/分类 99/99。
