# 十元理论每小时运行记录

> 本文件是唯一活动运行账本。任何理论轮次，无论成功、无可靠进展或失败，都必须原位更新本文件；不得再新建 `十元理论每小时运行记录_*补记.md` 作为替代账本。

## 1. 强制规则

1. 每轮开始先记录当前 `main` SHA。
2. 每轮只审计一条十元生、克、补关系；流程修复轮须明确标记“非理论关系审计”。
3. 每轮必须记录：队列状态、对象分层、候选机制、正反例、最近邻、拿掉测试、反向测试、动态链后果、95%门槛、修改文件、理论提交 SHA、失败原因和下一条关系。
4. 没有新证据时只写简短“无可靠进展”，不得重复扩写完整专项审计。
5. 需要同步状态时直接修改现行正本；不得再用几百行 `current-patch` 代替正本原位修正。
6. 写入前重新读取本文件 blob SHA；无法安全原位更新时，本轮必须记为失败，不得另建补记规避。
7. 理论任务不承担仓库层级、索引和补丁生命周期治理；治理工作进入独立治理任务。
8. 三元与十元并行，不建立父子派生。

## 2. 验收规则

```text
定时器已触发
≠ 研究已完成
≠ 文档已修改
≠ GitHub 提交成功
```

只有提交已从 GitHub 重新读取，并确认 SHA、修改文件和具体内容真实存在，才能写“提交成功”。

#### 对象分层

本轮不判断人物稳定本体、当前状态、行为功能、光影、场景、时间关系、关系位置或显影；处理对象仅为：核心关系正本、关系状态补丁、正式运行账本及其归档副本。三元与十元定义均未改写。

#### 候选机制

- 候选 A：继续让 `current-patch` 覆盖未原位同步的核心表，并继续新建分散补记。后果是读取顺序持续分叉，正本与提交说明不一致；否决。
- 候选 B：直接把已确认的“未锁定状态”写回核心表，将补丁降为历史入口；把旧账本原样归档，重新启用唯一主账本。后果是读取链重新单一化且不丢历史材料；采用。

#### 正例与反例

- 正例一：`zx 生 zn` 已经在核心表原位标记“语义待验收”，读取状态清楚。
- 正例二：旧账本 blob 可直接归档，证明无需以“文件太长”为理由另建补记。

- 反例二：主账本 blob 长期停留在 2026-07-19，而连续十轮写入独立补记，违反唯一账本要求。

本轮不是理论分歧处理，也不是重审 `zn 生 n` 或 `xz 生 zx`。只同步两份专项审计已经明确给出的状态：几何位置保留、正式机制未锁定。
