# strict v2 canonical 反测｜辛德勒正例说明“被保护者本人是 anchor”不能自动否决 x→zn

## 1｜本轮结论

火轴研究总纲当前新增纪律：

> 被保护者本人可直接构成 same-window 原则对象；operations x 不因组织这些人而自动获得对象构成地位。

这条纪律用于打掉《卢旺达饭店》Paul 的过宽 `x→zn` 归因是有价值的，但若被解释成：

> 只要被保护者本人已经现实存在，任何保护空间、资源系统、用工/庇护边界都只能算执行接口，不能再支持 `x→zn`，

就会再次与 L2 canonical 明列的《辛德勒的名单》正例冲突。

本轮裁决：

```yaml
people_are_reality_objects: true
people_presence_alone_blocks_x_to_zn: false
current_canonical: retained
L2_change: forbidden
```

---

## 2｜canonical 已经明确允许“人存在 + x 仍补现实保护边界”

L2 `zn补x` 正本把辛德勒中后期工厂保护阶段列为正式正例：

- `zn`：这些被迫害者应被救，且在持续耗财、低收益和风险下仍继续投入；
- `x`：工厂、资金、用工/保护安排、迁厂资源等现实掌握边界；
- `zn→x`：救人原则改变工厂与资源用途；
- `x→zn`：这些现实资源让救人原则形成具体受保护群体、持续保护范围与现实庇护。

这里被保护者当然在 `x` 进入以前就已经作为现实的人存在。

如果“人本人已经是 anchor”足以自动否决 `x→zn`，辛德勒 canonical 正例会被直接打掉。

因此 canonical 真正区分的不是：

```text
有没有现实的人存在
```

而是：

```text
这个 x 是否把原本只是‘这些人应被救’的现实对象，
进一步组织成一个可持续、可保护、可调用、具有明确我方边界的现实保护范围。
```

---

## 3｜两类 anchor 必须拆开

### A｜person/object anchor

被保护者本人提供：

- 原则面对谁；
- 谁正在受害；
- 主体当前可以对谁作出保护/抛弃选择。

这足以说明 `zn` 不是完全悬空。

### B｜protected-range / organized-boundary anchor

被测 `x` 可以额外提供：

- 哪一批人稳定进入我方保护范围；
- 持续资源如何围绕这批人投入；
- 哪个空间/组织边界能被反复调用用于保护；
- 当前保护对象如何从零散个体变成稳定、可持续的现实群体边界。

current canonical 的 `x→zn` 允许 B 在 A 已经存在时仍然成立。

所以：

> **person anchor 与 protected-range anchor 不是同一个变量。**

---

## 4｜拿掉测试

拿掉辛德勒的工厂、资金、用工/保护安排与迁厂资源：

- 被迫害者本人仍然存在；
- “这些人应被救”的 `zn` 仍然存在；
- 但原本由辛德勒企业体系形成的稳定受保护群体、持续资源投入范围、工厂庇护与迁移边界重新消失。

因此按 current canonical：

```yaml
person_anchor_retained: true
protected_range_anchor_lost: true
x_to_zn_gap_filling: true
```

这不是“宇宙唯一载体”要求，也不是说没有工厂就完全不能救任何人。

缺口只需要回到 current layer：

> 原本已经形成的稳定保护范围和现实边界是否重新消失。

## 5｜对 Paul 二审的影响

本轮不自动恢复《卢旺达饭店》Paul 99/94。

Paul 仍有独立问题：

1. 完整“酒店不被清空”的保护效果受 Sabena 产权、UN/军警、政治关系和谈判共同影响，不能全部归因给 Paul 的 operations `x`；
2. Paul 的被测 `x` 若只缩到房间、登记、员工和内部运营，是否足以单独形成可归因于他的稳定 protected-range anchor，仍低于95。

所以：

```yaml
restore_paul_automatically: false
```

本轮修正的是**通用门禁解释**：

> 不能仅因为“被保护者本人已经是现实对象”，就把一切保护空间/资源边界降格为纯执行接口。

必须继续区分：

- people/object anchor；
- protected-range / organized-boundary anchor；
- execution-only interface。

## 6｜对 strict v2 的新增纪律

建议 L4 后续使用：

```text
被保护者本人存在
≠
保护范围已经成立
```

以及：

```text
people anchor
≠
protected-range anchor
```

判断 `x→zn` 时应问：

1. 被测 `x` 是否只让主体“更容易做事”？
2. 还是它真实形成了一个此前不存在的稳定对象集合、保护范围、资源边界或我方空间？
3. 拿掉 `x` 后，这个稳定范围是否当前层真实消失？
4. 这个范围能否高纯归因给被测主体的 `x`，而不是第三方共同构成？

只有 2+3+4 通过，才支持 protected-range 型 `x→zn`。
