# 高置信结论直写与待用户确认门控协议 v1.0

## 1. 门控原则

本协议中的百分比衡量的是“用户会认可该判断或改动”的把握，不是假装精确的事实概率或理论真值概率。

```text
认可把握 ≥ 95%
→ 独立完成推理
→ 修正文档
→ 完成校验
→ 提交并推送 GitHub
→ 汇报新增结论、修改文件和提交记录

用户可能给出不同答案的概率 > 5%
→ 不替用户选择理论分叉
→ 先完成规定的独立推理
→ 写入并维护《待用户确认问题队列》
```

证据不足但答案可以通过补充资料、实读或机械核验解决时，优先标为“待补证”，不冒充必须由用户判断的问题。只有剩余差异涉及用户拥有的概念边界、价值判断、解释优先级或正本取舍时，才进入确认队列。

## 2. 直接落库标准

同时满足以下条件，才可直接完成：

```text
对象层已经冻结；
结论没有跨对象或跨层借证；
最近邻候选已经排除；
拿掉测试不推翻结论；
正反例没有形成同强度解释；
不改变用户尚未确认的概念边界；
与现行正本不存在未解决冲突；
对用户认可度的判断达到95%。
```

直接完成不等于可以跳过推理。提交前必须留下足以复核的证据、影响范围和理论后果。

## 3. 进入确认队列前必须完成的推理

每个候选问题必须先独立完成：

```text
1. 对象分层
2. 候选机制
3. 正例
4. 反例
5. 最近邻排除
6. 拿掉测试
7. 理论后果
```

不允许把“我不确定”直接转交给用户。队列只保留已经压缩到一个具体差异、且该差异确实需要用户拥有的判断权才能收口的问题。

## 4. 具体人物情境改写

抽象问题必须同时改写成一个可想象的人物情境。人物情境至少包含：

```text
谁；
处于什么当前状态；
做了什么；
在什么场景；
经过怎样的时间关系；
与谁处于什么关系位置；
真正需要用户判断的分叉是什么。
```

光影只能写为观看方式和显影辅助，不能替代人物、行为或关系证据。

## 5. 对象层纪律

始终分别记录：

```text
人物稳定本体
当前状态
行为功能
光影
外部场景
时间关系 / 时间结构
关系位置
```

人物核心锚点优先保持稳定。变化优先落在：

```text
当前状态
关系位置
显影强度
行为功能
场景承载
时间压力
动态链阶段
关系作用量
```

不得用职业、服装、光影、场景气氛、单次行为或表面关键词代替三元或十元判定。

## 6. 三元与十元边界

```text
三元与十元并行判断、互相校验；
三元不是十元的父级；
十元不是三元的子类；
三元比例不能生成十元点位；
十元公式不能反推唯一三元比例。
```

发生冲突时，返回原始证据与对象归属，不用父子派生关系强行圆合。

## 7. 队列字段与状态

每个项目必须包含：

```text
ID
状态
抽象问题
具体人物情境
助手已完成的推理
剩余具体差异
为何必须由用户判断
相关正本与提交
更新时间
```

推荐状态：

```text
待用户确认
用户已回答·待回写
已解决
```

ID 使用 `UQ-YYYYMMDD-NNN`，创建后不得改变。

## 8. 去重与解决流程

新增前按“抽象问题 + 具体人物情境 + 受影响正本”检查重复。已存在的问题只更新推理、证据、状态和时间，不再创建新 ID。

用户回答后：

```text
把答案写回相关正本；
更新受影响案例与索引；
完成校验；
提交并推送 GitHub；
把项目从活动队列移入同文件的“已解决记录”；
记录用户答案、落库位置和解决提交。
```

## 9. GitHub 提交纪律

```text
只暂存本轮明确相关文件；
混杂工作区不得使用 git add -A；
提交前检查 diff 与格式；
远端落后或分支关系不清时，不直接污染 main；
提交记录必须回写到相关队列项或解决记录；
GitHub 工具、认证或分支安全条件缺失时，文档可先完成，但必须明确标记“待发布”，不得虚报提交成功。
```

## 10. 最终封存

```text
高置信结论直接完成，不把机械确认转嫁给用户。
真正的理论分叉先推理到底，再交给用户决定最后一厘米。
人物核心优先稳定，变化优先落在状态、关系、显影和动态链。
三元与十元并行，不构成父子派生。
```
