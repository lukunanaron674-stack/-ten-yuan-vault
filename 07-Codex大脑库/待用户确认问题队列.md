# 待用户确认问题队列

## 用途

本页是自动任务与用户确认之间的持久交接区。每次自动任务必须先读取本页，再读取 GitHub 当前正本与最近提交；不得依赖上一轮对话中的临时记忆。

## 进入队列的门槛

只有满足以下条件的问题才可进入：

- 助手已经完成正本核对、对象分层、候选机制、正反例、最近邻排除、拿掉测试与理论后果；
- 助手判断用户给出不同答案的概率超过5%；
- 该分歧会真实改变十元定义、关系语义、五大主题边界或动态链规则；
- 问题已经改写成具体人物、阶段、关系和可观察差异；
- 问题不能仅靠继续查文档、补证或清理旧库独立解决。

入口、索引、旧文污染、重复规则、对象层混淆、端点正本升级导致的旧问题失配等治理事项，不得推给用户。

## 提问格式

每项必须包含：ID、状态、抽象问题、具体人物情境、助手已完成的推理、剩余具体差异、为何必须由用户判断、相关正本与提交、更新时间。

抽象问题必须改写成用户可以凭人物感觉回答的具体情境，不直接问“A生不生B”“A克不克B”或“它是不是本体”。

## 确认规则

每次最多提取1—2个最高价值问题。用户回答后，先写回正本与受影响案例，再把项目移入已解决记录。已被新端点或新正本覆盖的问题直接标记为`superseded`，不得继续提问。

### UQ-20260718-003

- **状态**：待用户确认
- **抽象问题**：现行 `x=归我掌握` 口径下，`nx生x` 是否拥有独立于 `z克nx` 的关系机制。
- **具体人物情境**：老板甲原本只掌握项目目标，员工乙长期不抢方向、不提出自己的安排，也不主动取回任务与时间的决定权。随后甲逐步把乙的工作顺序、时间、资源使用和对外口径都纳入自己的控制。情境A中，甲没有持续施压，只是乙每次都把方向位置空出来，甲的掌握范围因此自然扩大；情境B中，甲持续表达、决定、要求和占位，乙被一步步压退。
- **可观察差异**：A强调“乙不占方向位置，使甲原有的掌握边界获得扩张条件”；B强调“甲主动占位并压缩乙的选择空间”。结果相似，但启动源和目标变量不同。
- **助手已完成的推理**：旧“欲望积压”机制依赖已废止的旧 x 口径。现行 x 是具体对象、资源、权限和关系归我掌握。候选一是 nx 的不认领方向为他者既有 x 扩张提供条件；候选二是所有有效案例仍需要对方主动占位，因此只是 `z克nx` 伴随 x 增长，`nx生x` 只保留几何位。
- **正例候选**：长期由家长代为决定生活而本人持续不取回决定权；团队成员持续把任务与资源安排交给负责人，使负责人控制范围逐步扩大。
- **反例**：一次授权或临时委托，主体仍保留否决权；对方凭职位或强迫接管，主要是外部权力或 `z克nx`。
- **最近邻排除**：若源端点是 z 的持续占位、目标变量是 nx 的选择空间缩小，则判克；只有拿掉 z 主动加压后，控制边界仍因 nx 持续让位而扩张，才支持独立生位。
- **拿掉测试**：拿掉员工乙“不占方向”后，若老板仍凭职位扩大控制，案例不依赖 `nx生x`；拿掉老板主动施压后，若控制边界仍扩张，才支持该关系。
- **反向测试**：`x生nx`只能说明控制可能迫使他人服从，不能证明对方形成稳定 nx；反向不对称。
- **理论后果**：若成立，只能锁定关系层的窄机制，不改写人物稳定本体；若不成立，`nx生x`保持几何候选。
- **为何必须由用户判断**：该差异决定 `nx生x` 是独立正式关系还是几何候选，并影响母行能否正式调用。
