# F12 边栏实战经验 v1.0

## 一句话总结

F12 能跑，但不适合长时间无人值守。手动逐轮推进+每轮归档是最稳的用法。

## 核心结论

| 结论 | 说明 |
|------|------|
| **别指望 AUTO** | AUTO 模式下工蜂频繁断连，且归档不自动保存。跑 2-3 轮就卡 |
| **手动逐轮推进** | NEXT_ROUND → 等生成 → ARCHIVE_LATEST → 保存文件。最稳 |
| **每轮必须立即归档** | 页面刷新或下一轮发出去，上一轮内容就丢了 |
| **BIND+INJECT 是命门** | 必须用户当前活跃标签是 ChatGPT 页面才能注入工蜂 |
| **桥重启可救活** | 扩展心跳停了 → kill bridge node → 重启 server.js → 扩展重连 |

## 实际操作流程

`	ext
# 1. 启动桥（如果没跑）
node server.js  # 在 local-bridge/ 目录

# 2. 用户切换到 ChatGPT 标签页
# 3. 绑定+注入
BIND → 检查 activeTabId 是否 ChatGPT → INJECT

# 4. 加载任务
MULTI_COMMAND LOAD_TASK <tabId> <tasks_file>

# 5. 手动逐轮
NEXT_ROUND → 等 30-90 秒 → ARCHIVE_LATEST → 保存文件
`

## 工蜂断连恢复

`	ext
1. 刷新 ChatGPT 页面
2. BIND（确保绑到 ChatGPT 标签）
3. INJECT
4. 检查 bridge-state.json 中 tab 状态
5. 如 tab 状态丢失 → 重新 LOAD_TASK
`

## 归档提取技巧

| 方法 | 可靠性 | 说明 |
|------|--------|------|
| ARCHIVE_LATEST | 中 | 抓最新一条 assistant 回复，页刷了就空 |
| 心跳 lastMessage | 低 | 偶尔包含全文，但会被下次命令覆盖 |
| SEND_CURRENT | 低 | 常卡在 delivered，工蜂不响应 |

## 多标签限制

- BIND/INJECT 是全局的，每次只能绑一个活跃标签
- MULTI_COMMAND 可路由到指定 tabId——但该 tab 必须有工蜂
- 不能同时跑多个 AUTO 标签——只有一个工蜂在线

## 坑

1. **编码**：PowerShell 读 F12 输出会乱码，用 Node.js 读文件正常
2. **桥状态文件过大**：bridge-state.json 保存所有历史命令，/status 接口超时
3. **心跳不是状态**：status=idle + age=5s 不代表 ChatGPT 已生成完
4. **翻页丢失**：ChatGPT 页面如果自动滚动或刷新，DOM 里的回复可能被清

## 建议

- F12 适合：单轮查资料、单轮角色分析
- F12 不适合：8 小时 AUTO 巡航、无人值守批量处理
- 备选方案：Playwright 脚本直接操控 ChatGPT 页面，比扩展可靠
- 直接写卡：对熟悉的作品，自己写比等 ChatGPT 更快更准
