# Agent 自主性等级 1-10 与现有系统评级

> 目的：用统一尺度判断 Agent 的“自主性 / 状态维护 / 工具调用 / 调度能力”，避免把“角色设定很多”误当成“Agent 等级高”。

## 一、1-10 级定义

| 等级 | 名称 | 能力 | 必需组件 |
|---|---|---|---|
| L1 | 回答器 | 单次输入→单次回答 | LLM + Prompt |
| L2 | 角色化回答器 | 固定专业视角、固定输出格式 | 职责边界 + 输出模板 |
| L3 | 限定上下文 Agent | 围绕一个固定问题持续工作 | 问题节点 + 父目标 + 限定上下文 |
| L4 | 状态 Agent | 记住上次做到哪、已尝试什么、当前卡点 | 状态字段 + 历史记录 + 版本 |
| L5 | 工具 / 专项 Agent | 能查索引、读文件、调用工具或执行单一专项动作 | 工具权限 + 调用规则 + I/O 协议 |
| L6 | 行动 Agent | 能依据状态决定 ACCEPT / MODIFY / RETRY / REPLAN / 下一步，并执行有限循环 | 状态机 + 决策规则 + STOP / DONE 条件 |
| L7 | 巡航 / 调度 Agent | 被定时唤醒后主动扫描状态、选择下一 Agent/动作并推进到外部阻塞 | 调度器 + 优先级 + 预算 + blocker + NO_OP |
| L8 | 动态分解 Agent | 能把新问题拆成子问题，并按模板临时生成/挂载专项 Agent，完成后回收 | 问题树 + Agent 模板库 + 生成规则 + 回传/销毁协议 |
| L9 | 自治问题组 | 多 Agent 并行/协同，具有冲突治理、锁、版本、回滚与资源预算 | 权限系统 + 锁 + 冲突裁决 + 回滚 + 审计 |
| L10 | 自治系统 | 可自己发现问题、建树、调度、验证、关闭并进入下一批问题 | 完整目标系统 + 问题系统 + 长期记忆 + 治理 + 人工接管 |

### 判级原则
- 等级按“实际拥有的能力”判，不按 Prompt 写得多不多判。
- 能做专业判断，不等于能调度别的 Agent。
- 能每小时被调用，不等于 L7；只有能自己读状态、选下一动作、NO_OP/STOP 才算 L7。
- 能创建“任务”不等于 L8；L8 要能创建与子问题绑定的临时专项 Agent，并有回传与销毁规则。
- 正式生产 Agent 不应全部升到 L8+。高自治集中在导演/问题调度层，专业 Agent 保持窄职责更稳定。

## 二、当前每小时 Agent 系统评级

### 当前正式自动调度：L7
依据：
- 每个 Macro Tick 读取唯一状态源。
- 不再把所有 Agent 全部唤醒，而是选择当前 primary Agent。
- 可在同一 Macro Tick 中按依赖链连续调用多个岗位。
- 遇真实外部阻塞才 STOP。
- 相同 state_hash 可 NO_OP。
- 有优先级、最大讨论轮、视觉重试和执行重试预算。
- 能在 production / learning 两条轨之间按状态路由。

当前**不是 L8**，因为：
- 只调度现有固定 Agent；
- 尚未按“问题节点”动态创建临时专项 Agent；
- 尚无“子 Agent 生成→绑定子问题→结果回传→自动销毁/休眠”的正式协议。

### 从 L7 升到 L8 的最小新增件
1. `PROBLEM_NODE_SCHEMA`：问题节点、父目标、原因链、证据、DONE 条件。
2. `TEMP_AGENT_TEMPLATE`：专项 Agent 的最小 Prompt/输入/工具/权限模板。
3. `SPAWN_RULE`：何时允许问题 Agent 生成专项 Agent。
4. `RETURN_PROTOCOL`：专项 Agent 只能把结构化结果回传原问题。
5. `LIFECYCLE`：DONE / BLOCKED / EXPIRED 后休眠或销毁。
6. 每问题预算：最大子问题数、最大 Agent 数、最大轮次/Token/工具调用。

## 三、旧每小时 B 链映射与等级

| 旧模块 | 当前正式归属 | 评级 | 原因 |
|---|---|---:|---|
| B0 / DIRECTOR_MASTER | AG-00 导演 + AUTO_DISPATCH | L7 | 能读全局状态、选择下一岗位、连续推进到外部阻塞 |
| B1 :05 素材索引 | AG-04 素材 Agent | L6 | 能查真实素材、判断 READY/MISSING、触发缺口路径，但不能改全局状态 |
| B2 :15 十元 / 动态链 | AG-02 十元 Agent | L5 | 专项结构判断 + 状态化结果，不拥有全局调度 |
| B3 :25 镜头 / H3 描述 | AG-03 分镜 Agent | L6 | 把上游结果转执行镜头、维护 opening/closing state、可形成下一执行动作 |
| B4 :35 质检 | AG-06 风格审核 + AG-08 视频审核 | L6 | 可 PASS/RETRY/REPLAN，生成定向返工，但不自行推进全局指针 |

> 旧的 “B1→B2→B3→B4 每小时全跑” 已被当前 `AUTO_DISPATCH_PROTOCOL` 替代。现在每 tick 只按状态唤醒必要 Agent，能串行推进则继续，遇真实外部阻塞才停。

## 四、当前正式 Agent 库逐个评级

> 当前 `01_Agent库` 实际为 **12 个正式岗位（AG-00～AG-11）**。原“20_代理库”已于 2026-10-01 并入本系统并移除平行维护副本，所以“20”现在是系统目录/历史命名，不代表仍有 20 个独立正式 Agent。

| Agent | 当前等级 | 主要理由 | 建议上限 |
|---|---:|---|---:|
| AG-00 导演 Agent | **L7** | 唯一全局状态合并者；决定下一岗位；处理冲突、返工和外部阻塞；绑定 AUTO_DISPATCH | L8 |
| AG-01 剧本 Agent | **L5** | 读取状态与主题结果，产 script_result；能提出 THEME_REPLAN，但不拥有流程 | L6 |
| AG-02 十元 Agent | **L5** | 专项十元/动态链判断；提交 delta；不可改主题/剧情/全局指针 | L5 |
| AG-03 分镜 Agent | **L6** | 状态化镜头编译、时间段、运镜、H3 Prompt、连续性输出；可形成执行级下一步 | L6 |
| AG-04 素材 Agent | **L6** | 查询真实资产、hash/locator、判断 READY/MISSING、请求补素材；受 manifest 与门禁约束 | L6 |
| AG-05 生图 Agent | **L5** | 仅在明确 ASSET_MISSING 时执行单一补图动作；输出 PENDING 资产后退出 | L5 |

| AG-07 H3 渲染 Agent | **L6** | 调真实执行任务、读错误、按错误类型有限重试；必须等待 executor_receipt | L6 |
| AG-08 视频审核 Agent | **L6** | 能 PASS/RETRY/REPLAN、生成 retry packet 与 closing_state；无权创建 next_shot | L6 |
| AG-09 主题 Agent | **L5** | 主题计划/审计、研究证据与结构化输出；最多一次 THEME_AUDIT，不拥有调度 | L5 |
| AG-10 世界观 Agent | **L6** | 兼具扩展、审核、治理、索引、角色种子与世界提案；可主动维护但受 Canon 门禁 | L6 |
| AG-11 角色 Agent | **L6** | 可 BUILD/UPDATE/AUDIT、写角色卡、发 Codex 工单、请求世界/十元复核；多状态门禁 | L6 |

## 五、结构判断

当前最健康的结构是：

```text
L7：AG-00 导演 / AUTO_DISPATCH
  ↓
L5-L6：主题 / 世界观 / 剧本 / 十元 / 角色 / 分镜
  ↓
L5-L6：素材 / 生图 / 风格审核 / H3 / 视频审核
```

不要把所有专业 Agent 同时升级到 L7-L8。

原因：
- 专业 Agent 越窄，越容易审计与复现；
- 全局状态必须保持单写者；
- “主动性”应放在调度层和未来的问题代理层，而不是让每个岗位自己抢任务；
- L8 最适合新增为“问题 Agent / 临时专项 Agent”体系，而不是改造现有生产岗位。

## 六、下一版建议：问题树 Agent 层

建议在现有生产 Agent 系统**上方**新增一条独立的问题解决轨：

```text
目标系统
→ 问题树
→ Problem Agent（L7）
→ 需要专项能力？
   → 临时专项 Agent（L5-L6）
→ 回传证据/结论
→ 审核
→ CLOSE / CONTINUE / SPLIT
```

再由总控把已经收束成“明确执行动作”的结果交给当前 12 Agent 生产系统。

这样：
- **问题系统负责为什么没做到**
- **Problem Agent 负责盯住问题直到闭环**
- **现有 12 Agent 负责专业判断与实际生产**
- **AG-00 负责生产系统调度**
- **未来 L8 只负责按问题生成临时求解器**

## 七、一句话结论

> 目前 Agent 系统真实水平是“**L7 总控 + L5/L6 专业岗位**”；这比把十二个岗位全做成高自治更合理。下一步若要获得你说的“每小时批量解决问题”的主观能动性，应新增“问题树 + L7 Problem Agent + L8 临时专项 Agent 生成协议”，而不是继续增加固定岗位。
