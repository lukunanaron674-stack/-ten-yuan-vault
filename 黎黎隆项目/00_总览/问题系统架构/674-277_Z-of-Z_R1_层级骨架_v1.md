# 1｜Z-of-Z 四层骨架

## Z0｜总控 Z
定义：整个问题系统最终要实现的最高目标。

当前候选：
> **Z0：让 74 能持续、可校准地控制 AI / Agent / Worker 去解决问题，并把规则、NX、执行路径和结果稳定回写。**

体量建议：**80–100**

规则：
- Z0 只负责方向与最终验收。
- Z0 不直接挂大量细粒度 XN。
- Z0 的 XN 必须是“总原则级 XN”，例如：
  - 所有子 Z 必须可追溯到 Z0；
  - 未验证 XN 不得冒充事实；
  - 缺 PATH 不得宣称 Z 已落实；
  - 高风险/高 NX 的决策必须允许 74 接管。

## Z1｜主域 Z
定义：Z0 为了成立，必须拥有的几个独立能力域。

建议体量：**50–79**

当前候选主域：
- Z1-A｜目标/问题结构治理
- Z1-B｜XN 规则获取、校准与迁移
- Z1-C｜NX / 偏好 / 人类判断补充
- Z1-D｜Agent 主权与责任
- Z1-E｜PATH / 现实执行与跨端落实
- Z1-F｜状态、证据、版本、回传
- Z1-G｜长期运行与恢复 / 调度

说明：这 7 个是候选，不在 R1 宣告最终冻结；R2 再判必要组成/依赖/支持/冲突关系。

## Z2｜能力 Z
定义：某个主域内部，一个可以单独评价、单独分配 XN、单独验证的能力目标。

建议体量：**20–49**

例：
Z1-E「PATH / 现实执行」可拆：
- Z2-E1｜有可调用工具
- Z2-E2｜有权限
- Z2-E3｜有触发器
- Z2-E4｜有共享状态
- Z2-E5｜有结果回传

每个 Z2 必须能拥有自己的：
- XN_SET
- NX_GAPS
- AUTHORITY
- PATH
- expected_xn_fit
- verified_xn_fit
- done_condition

## Z3｜原子执行 Z
定义：已经小到可以直接设计一次验证/施工/讨论闭环的目标。

建议体量：**1–19**

例：
- “4080 Worker 能读取 READY_FOR_RENDER 队列并领取一条任务”
- “角色审核网页的 ACCEPT 状态能回写素材 manifest”
- “H3 失败后只重跑当前 10–11s block”

Z3 的目标是：
> 一次有限任务能够证明“成立 / 不成立 / 缺什么”。

Z3 以下原则上不继续拆成正式 Z。
继续出现的内容优先记录为：
- step：执行步骤
- xn：规则
- evidence：证据
- blocker：阻塞
- nx：尚未形式化判断

而不是继续造 Z4/Z5。

# 2｜体量不是层级的绝对判定

`z_volume 1–100` 是体量，不等于层级编号。

默认区间：
- Z0：80–100
- Z1：50–79
- Z2：20–49
- Z3：1–19

但允许例外。

层级真正由“父子功能关系”决定：
> 上层 Z 是否必须通过下层 Z 才能成立。

所以不能因为一个目标 volume=60 就自动判定为 Z1。

---

# 3｜继续拆分条件

任一条件成立，就应该继续拆：

1. 当前 Z 需要 **两组以上明显不同的 XN** 才能约束。
2. 当前 Z 同时存在 **不同责任主体 / 不同权力边界**。
3. 当前 Z 同时跨越 **不同 PATH / 不同执行端**。
4. 当前 Z 的 expected_xn_fit 很低，原因是内部存在多个不同子目标。
5. 当前 Z 无法给出单一可观察 DONE 条件。
6. 当前 Z 中一个 blocker 只影响其中一部分，而不该卡死整个 Z。
7. 当前 Z 的 NX 来自多个互不相同的判断维度。

一句话：
> **如果一套 XN 不能自然地约束整个 Z，就把 Z 拆小。**

---

# 4｜停止拆分条件

满足以下多数条件即可停止：

1. 一个有限实验 / 工单能直接验证。
2. 有一个明确 done_condition。
3. 可以指定一个主要 owner。
4. 可以明确谁有 decision / execution / review 权。
5. XN_SET 不再混有彼此无关的规则束。
6. 一个 blocker 可以明确定位到这个 Z。
7. 再拆只会变成执行步骤，而不会改变判断或权力。

停止后，不再制造更多正式 Z。
