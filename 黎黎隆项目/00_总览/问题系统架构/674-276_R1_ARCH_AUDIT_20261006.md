## 3｜当前重复 / 容易混层的地方

### 1. Goal 与 Z
现有 Goal 已承担“上层目标”语义。
新架构不能再造平行 Goal。
建议：
- `Z` 作为 Goal 的十元/控制层表达；
- 数据层保留兼容：`goal == z_statement`，新增 `z_id` / 层级字段。

### 2. required_agent 与主权
`required_agent` 只回答“谁来做”，不回答：
- 谁能决定
- 能决定到什么程度
- 何时升级
- 何时74接管

所以需要新增 authority，而不是替换 required_agent。

### 3. status 与 PATH state
问题状态不能混成现实执行状态。
建议分：
- problem_status
- asset_status
- path_status
- authority_status

### 4. known / unknown 与 XN / NX
不能直接把：
- known = XN
- unknown = NX

因为 XN 是规则结构，NX 是尚未形式化/未被覆盖的判断与关系。
两者只能关联，不能同义替换。

### 5. BLOCKER 与缺 PATH
BLOCKER 是当前阻塞状态；
PATH 缺口是阻塞原因的一类。
例如：
`BLOCKED(reason=NO_EXECUTION_BRIDGE)`
而不是把 PATH 当成新的问题状态体系。

R2/R4 必须遵守：

1. `黎黎隆问题系统.canvas` 仍是唯一问题地图。
2. Problem State v1 不删除，只做兼容扩展。
3. MAIN-13/14/15/16/17 继续作为对应问题的知识宿主。
4. 现有 Q-ID / MAIN-ID / SUB-ID 不因 Z/XN 架构重新编号。
5. D1-D3 问题深度不与 Agent L1-L10 混用。
6. Canvas 只承载导航 / 状态 / 关键控制字段；详细证据留 Markdown。
7. Linear 继续是调度与回传，不取代 canonical。
8. 候选 XN / 迁移规则 / AI proposal 不得直接提升为 VERIFIED。
9. 用户审美、身份、价值判断仍保留 USER_REVIEW 最终权。
10. 不能因“有规则”宣称“现实可执行”；必须单独检查 PATH。

## 5｜R1 的核心发现

### 发现 A｜不是重做问题系统
现有系统已完成“问题治理”和“状态治理”的大半。
真正缺的是一层 **Z/XN/NX/PATH 控制视图**。

### 发现 B｜最重要的新字段只有四簇
1. **Z 层级与达成等级**
2. **XN 来源、覆盖等级与 M1 评价**
3. **NX 补充 / 人类反馈**
4. **PATH / 主权 / 现实执行能力**

### 发现 C｜新架构应当“挂在 Problem State 上”，而不是替换 Problem State
推荐关系：

`Problem State v1`
→ 挂 `Z_STATE`
→ 挂 `XN_SET`
→ 挂 `NX_GAPS`
→ 挂 `AUTHORITY_STATE`
→ 挂 `PATH_STATE`

### 发现 D｜M1–M4 与现有 MAIN 的映射
- M1 评价：跨 MAIN-15/16/17，新增 XN 评价字段
- M2 主权：主要落 MAIN-16
- M3 NX/偏好/素材证据：主要落 MAIN-13/14/15
- M4 大小目标/依赖/状态：主要落 MAIN-17 + Problem State v1
- PATH：MAIN-14/15/16 的共用横切层
