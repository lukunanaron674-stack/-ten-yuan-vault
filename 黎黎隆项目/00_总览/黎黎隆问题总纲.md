## Linear Issue Governance｜工单容量、母单仓库与新建前置门（2026-10-07）

> 本节是《黎黎隆》项目内 Chat / Linear / Codex 的工单创建硬规则。来源/系统责任归属：Linear 674-77。任何 Chat、Agent、Codex 在准备新建 Linear Issue 前，必须先执行本节的 `ISSUE_CREATE_PREFLIGHT`。

### 1｜核心定义：Issue 不是一次任务

Linear Issue 默认视为**长期容器 / 系统 / 仓库 / 调度器**，不是一次性任务编号。

以下对象默认只使用母单内部编号，不新建 Linear Issue：

- 一轮研究、一次讨论、一条子问题；
- 一批图片、一次 ComfyUI RUN、一次返工；
- 一个角色、一个角色版本、一次 L1/L2/L3 延展；
- 一段 H3 视频、一个 10–11 秒块、一个 LongTake block；
- 一个实验样本、一个 seed、一个 prompt；
- 一次审核、一次 PASS/FAIL、一次 manifest 更新；
- 一篇论文中的单一步骤、一个小节；
- 一个故事单集、一个镜头或单次失败记录。

内部编号可以无限扩展；Linear 全局 `674-XXX` 只用于真正需要独立生命周期的长期容器。

### 3｜图片固定流转

```text
674-124  图片生产
   ↓
674-154  全量资产索引 + Review Manifest
   ↓
674-173  USER 人工审核
   ↓
674-125  FAIL / RERUN 返工
   ↓
674-124  再生产
```

规则：

- 一批图不新建 Issue；使用 `124-RUN-*`。
- 每张图使用稳定 `asset_id` + SHA256，不用 Issue ID 代替资产 ID。
- 154 负责“该来的图都来了”；173 只负责用户判断；125 只接返工。
- PASS / FAIL / MAIN_REFERENCE 必须绑定资产 ID / SHA。
- 同一个仓库 Issue 可以持续追加图片、附件、manifest、评论和 receipt。

### 4｜视频固定流转

H3 / 视频默认全部进入 674-216，不按视频条数创建 Issue。

示例：

```text
216-H3-20261007-001
├─ VID-0001
├─ VID-0002
└─ manifest

216-LT-001
├─ BLOCK-01
├─ BLOCK-02
├─ BLOCK-03
└─ FINAL
```

单个视频、单个 block、单次失败、单次重跑都只是 216 内部记录。

### 5｜角色 / 问题 / 审核内部编号

角色使用数据编号而不是 Linear Issue：

```text
CHAR-044
├─ L1 / HEAD
├─ L2 / FOURGRID
├─ L3 / identity + world_role + ten_yuan
└─ H3 / VIDEO
```

问题与审核优先沿用母单内部树：

```text
173-1
173-1-1
173-1-2
173-2
...
```

只有某个内部节点真的需要**独立责任主体、独立状态机、长期阻塞关系或长期外部执行器**时，才考虑创建独立 Linear Issue；即使创建，也必须保留其母单内部语义编号。

### 6｜ISSUE_CREATE_PREFLIGHT｜创建新工单前置门

任何 Chat / Agent / Codex 准备调用“创建 Linear Issue”前必须按顺序判断：

```text
出现新任务 / 新问题
→ 查 674-77 / 本节 Governance
→ 查永久母单注册表
→ 现有母单能否承载？
   ├─ YES：禁止创建新 Issue；生成内部 ID / RUN-ID / CHAR-ID / IMG-ID / VID-ID / Q-ID
   └─ NO：继续判断
→ 是否是新的长期系统 / 仓库 / 调度器？
→ 是否具有独立责任主体或长期生命周期？
→ 是否需要独立 blocks / blockedBy / 状态机，且放在现有母单会造成真实管理冲突？
   ├─ NO：禁止创建新 Issue
   └─ YES：允许创建，并登记到母单注册表
```

**默认结论必须是“不创建”。** 新 Issue 是例外，不是默认动作。

### 7｜允许创建新 Issue 的最低条件

至少满足下列一项，并且现有母单确实无法承载：

1. 新的长期系统或长期仓库；
2. 新的固定 Worker / Agent 执行入口；
3. 与现有母单不同的独立生命周期 / 状态机；
4. 需要长期独立维护的 `blocks / blockedBy` 关系；
5. 新的顶级研究方向，且不是既有论文/问题总仓中的一个步骤；
6. 现有容器复用会导致责任、资产或状态彼此污染。

仅“内容很多”“想单独看”“这一轮很重要”“需要上传很多图/视频”都不是新建 Issue 的充分理由。

### 8｜Chat / Agent 执行约束

- 674-116 每轮发现新问题时，先执行 `ISSUE_CREATE_PREFLIGHT`，再决定内部编号还是新 Issue。
- 674-115 / 124 / 154 / 173 / 216 的普通运行只追加内部 run / asset / review / video ID 与 receipt。
- 不以 Linear Issue 数量表达工作量；工作量由内部记录、Manifest、Q、RUN、资产计数表达。
- 已有职责相同的 Issue 优先归并 / 归档旧单，不再复制新入口。
- 如果未读取本规则或无法确认母单职责，默认 **STOP_NEW_ISSUE**，先复用现有母单或回到 674-77 / 674-116 判断。

## 头像问题系统 v1｜正式冻结规则（674-91）

### 1｜节点层级

- `G0` 为总目标，`G1/Gx` 为分目标；正式问题树使用 `Q`、`Q.x`、`Q.x.x`，最多三级（D1/D2/D3）。
- `level` 是问题树深度的兼容字段，不得与 Agent 能力层 L1–L4 混用。子问题的 `parent` 必须指向现存父节点。
- 已可直接设计实验时停止拆分；不为树形完整度补空节点。

### 2｜正式 Q 准入

只有同时满足以下条件才建立正式 Q：

- 有具体头像资产、记录或用户反馈证据；
- 对父目标或父问题有直接影响，因果链清楚且不把相关性冒充因果；
- 有可观察、可判定的 DONE 条件。

“可能”“感觉”“更好看”、类别清单以及把解决方案改写成问题，都不能单独成为正式 Q。

### 3｜结果分流

- **DONE**：真实问题满足预先写明的 DONE 条件，证据和关闭依据已回写原 Markdown；Canvas 同步状态。
- **OPEN / BLOCKED**：问题有证据成立，但缺少输入、样本、权限、人工确认或其他必要条件。必须记录 `blocked_reason` 和 `unblock_condition`；不得为提高完成率提前关闭。若当前只证明验证缺口，要写成证据缺口，不得宣称视觉失败。
- **REJECTED / UNVERIFIED_HYPOTHESIS**：无证据假设、纯审美偏好、伪因果、同义重复、已由其他 Q 覆盖、把方案写成问题。只留 Markdown 审计记录，不分配正式 Q-ID，不进 Canvas；如重复，写明 `duplicate_of`。

### 4｜volume 与 impact_weight

- `volume` 1–10：问题自身波及范围。
- `impact_weight` 1–10：问题对直接父节点的影响强度。
- 二者不得混用，不代表工时或百分比，兄弟节点不要求加总为 10。

### 5｜Canvas 固定字段

头像分支正式 Q 节点使用 text node，只显示：Q-ID、问题名、level、volume、impact_weight、parent、status、Markdown 内链。保留原 Canvas、节点 ID、位置和父子关系；不为伪问题创建节点。详细证据与研究内容留在 Markdown。

### 6｜Markdown 固定字段

- Frontmatter：`q_id`、`level`、`parent`、`goal`、`volume`、`impact_weight`、`status`、`linear_issue`。
- 正文至少包括：问题一句话、为何影响父问题、当前证据、因果链、DONE 条件、当前结论、下一步；如适用，再记录 `blocked_reason` / `unblock_condition` 或“否决假设 / 伪因果 / duplicate”。
- DONE 卡必须留关闭依据；状态和来源变化回写原 Q 卡，不以 Linear 取代问题本体。

### 7｜拆分停止

达到三级、已能直接设计实验、继续拆分不会改变解决动作、子问题只是父问题换说法、或证据不足以区分原因时停止。后两类转为待验证假设，不继续造节点。

### 8｜人工审核边界

角色是否为同一人、审美身份是否成立、正面/半侧是否保持同人、是否接受视觉差异，必须由用户最终确认。Agent 可整理证据和提出判定方法，不替用户做审美身份判断。图像存在或规则初检通过不等于人工通过。

### 9｜v1 验证案例

- **DONE**：[[Q-CHAR-001.1_头部身份锚是否稳定继承]]——S10/H06 特定错配经修正并由用户确认。
- **OPEN / BLOCKED**：[[Q-CHAR-001.4_H04正面半侧身份继承是否有充分证据]]——存在 H04 原头像、四宫格和报告，但缺少正面/半侧锚点对照结论；这证明验证缺口，不证明 H04 已错配。
- **REJECTED**：[[Q-CHAR-001.3_可发散范围是否进入任务输入]]——“可发散范围普遍导致头像漂移”缺少输入/失败图配对与因果证据，不分配正式 Q、不进 Canvas。

### 10｜v1 代理边界

仅处理头像身份问题证据、因果树、原 Canvas/Markdown、验证步骤和结果；不自行生成或替换图片，不把候选提升为正式资产，不扩到全身、场景、剧情、分镜、H3 或其他生产流程。
