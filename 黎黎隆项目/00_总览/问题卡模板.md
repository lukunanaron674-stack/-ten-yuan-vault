# 问题卡模板｜Problem State v1

新问题先经 L1–L4 编译与审核，再决定新建或合并到既有 Q。L1–L4 是 Agent 交接层；`problem_depth` 的 D1/D2/D3 是问题树深度，两者不可混用。复制本模板时，先检查现有 Canvas、Q-ID 和来源，不能因模板而另建重复问题。

```yaml
---
q_id: "Q-DOMAIN-000"
scope: "lililong"
domain: ""
level: 1 # 兼容旧卡；问题树深度以 problem_depth 的 D1/D2/D3 为准
problem_depth: "D1"
parent: "G0 或现有父 Q-ID"
goal: "现有目标 ID"
parent_goal: "现有直接父目标或父问题"
volume: 1
impact_weight: 1
priority_score: 1
status: "OPEN"
linear_issue: ""
problem_statement: ""
known: []
unknown: []
tried: []
rejected: []
current_hypotheses: []
evidence: []
source_refs: []
current_version: "1.0"
next_decision: ""
done_condition: ""
required_agent: []
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
---
```

## 字段约束

- `q_id`：新问题才分配新 ID；重复问题更新原卡。已存在 Q-ID 不改名。
- `parent` / `goal`：只引用现存父 Q 或目标；D2/D3 子问题必须有真实父项，不可为了图上整齐虚构父子关系。
- `parent_goal`：写明此问题直接服务/阻塞的冻结目标 ID（G0–G9 或既有分目标）；D2/D3 的直接父问题另由 `parent` 写现存 Q-ID。不得把 G 目标编号与 D 深度混淆。
- `known`、`unknown`、`tried`、`rejected`、`current_hypotheses`：分别写事实、缺口、尝试、否决及尚待验证假设；不要混为一段摘要。
- `evidence` 与 `source_refs`：结论需能回到真实路径、Linear、版本或可观察结果。候选来源要标明候选状态。
- `current_version`：有效结论变化时递增；只改格式不递增。
- `next_decision`：写下一位执行者可采取的单一步骤。
- `done_condition`：写可观察、可判定的关闭条件；条件未被证据满足时不标 DONE。
- `required_agent`：列出现有专业代理；不在此创建新代理或扩展其权限。
- 正式 Q 才进入 Canvas；纯假设、重复项、范围外项留在现有审计段落，不分配新 Q-ID。

## Z 问题卡与体量标尺 v0.1｜2026-10-13｜USER 确认采用（日常交流/问题治理）

> 本节是 **Problem State v1 的兼容扩展**，不是第二套问题树、十元定义或旧评分的批量改写。来源：Linear 674-276（问题系统规则）、674-294（工单路由），Z-of-Z 历史研究见 674-277 R1–R4。**日常使用方式已获 USER 授权；体量评分权重与建卡阈值仍为 v0.1 待实证校准的工作约定。**

### 1. 默认交流顺序（按问题大小缩放）

- **判断**：一句话说明真实问题与当前结论。
- **Z｜真实问题**：问题边界、影响对象、证据，标注 \`z_volume_1000\` 与评分置信状态。
- **XN｜解决规则**：已有、候选、已验证要区分；不能把提案当成果。
- **NX｜未解缺口**：未知/反例/待审核/缺工具或路径；若无，明确写 \`NX=NONE_VERIFIED\`，不凭沉默宣称无缺口。
- **PATH｜下一步**：执行主体、输入输出、工单路由、单次最小动作。
- **DONE / STOP / EVIDENCE**：收口证据及边界；本地实际执行、Linear回执、USER审美三种证据不得混用。
- **真实进步**：只有新证据、真实状态变化或问题减少才算增量，不能以评论数/规则数算进步。

微小日常问题可压缩为几句话；不可因固定格式造成沟通负担。**先看最新 HOT / 当前事实，只处理真实增量；无变化 NO_OP，有新证据才更新，不为管理而管理。**

### 2. Z 体量：1–1000（与优先级、风险、工时、感受强度分离）

\`z_volume_1000\` 暂用 5 维 × 0–200，合计后最小记 1、最大 1000。每维需一句评分理由；资料不足记 \`UNSCORED\`，不装作精确。

| 维度 | 0–200 的判读对象 |
|---|---|
| scope_score | 影响范围：对象、流程、团队、系统的覆盖 |
| goal_impact_score | 对目标达成的影响，注意不是紧急程度 |
| dependency_score | 关联/牵连多少独立子问题、依赖、下游 |
| persistence_score | 一次性、跨轮次反复或长期结构性 |
| complexity_score | 独立验证、协调、技术处理的复杂度 |

\`z_volume_1000 = clamp(sum(五项),1,1000)\`；它是**人工估值/排序工具**，不是客观测量值，不等于问题已解决的百分比，也不能直接得出授权、优先级或父 Z 的真实完成度。可记 \`score_status: ESTIMATED | USER_CALIBRATED | NEEDS_EVIDENCE\`。

### 3. Z 卡准入门槛（候选政策，非自动创建门禁）

| Z体量 | 默认动作 |
|---|---|
| 1–99 | 微型 Z：直接解决/记录一句，不单建卡 |
| 100–299 | 小型 Z：保留在现有聊天/父 Q 内 |
| 300–499 | 候选 Z 卡：反复出现或独立 NX 需要跟踪时才建 |
| 500–799 | 正式 Z 卡候选：独立闭环、可追证才登记 |
| 800–1000 | 母级 Z 卡候选：必要时拆局部子 Z，各自 XN/NX/PATH |

**分数不是充分条件。** 建正式 Z 卡至少需要：具体真实问题与来源/证据；清晰 scope 和归属；区别于现存卡；有可验证 DONE/STOP；持续跟踪确有收益。反过来，高风险/紧急的小 Z 可以立即执行，不能被体量门槛延误。一次对话的小问题无需单独发卡。父/子 Z 是否成立取决于功能必要性，而非分数。

**重要：Z 卡 ≠ Linear Issue。** 任意新卡须先查现有 Q-ID、Canvas、Linear 674-294。默认复用母卡/已有工单的内部 Z-ID；只有另有真实独立生命周期、权限/阻塞/责任需求并通过 Recover Before Create 才允许新建 Linear Issue。不能因为体量 ≥500 自动创建工单。

### 4. 兼容旧量尺，不重写历史

- 此前项目头像 Problem State 的 \`volume=1–10\` 仍是 legacy 字段；\`impact_weight=1–10\` 仍代表对子目标的影响。
- 674-277 R1–R4 的 \`z_volume=1–100\` 记录作为**历史 Z-of-Z 量尺**保留；不得在没有新评估依据时直接乘10伪装成新体量。
- 新记录**新增字段** \`z_volume_1000\` + \`volume_scale: Z_1000_V0_1\`，旧字段不覆盖。旧量尺读入时显式标 \`LEGACY_10\` / \`LEGACY_100\`。
- Z0/Z1/Z2/Z3 是功能层级，D1/D2/D3 是项目问题树深度，L1–L4 是 Agent交接层级；三个层级互不等同。
- 十元的 XN 是情绪/十元符号，问题系统的 **XN 是解决规则**；十元 1–10 感受强度亦与本体量无关。

### 6. 首批仅为人工估值示范，不是冻结真值

- Linear 状态失真：\`Z-LINEAR-STATE\`，约 \`670/1000\`，XN=新鲜回执核状态；NX=全量差异清单未核实。
- H3 产片→审核→正式入库→知识回传断点：\`Z-H3-CLOSURE\`，约 \`850/1000\`，XN=run_id/SHA/USER审美/视频仓差量对账；NX=未收口数量及方法真实吸收证据。
- Linear 管理膨胀：\`Z-LINEAR-GROWTH\`，约 \`650/1000\`，XN=Recover Before Create/HOT；NX=旧号路由与异常生命周期。

以上 **3 个是说明例子**，不直接生成 Q-ID / issue、不改变任何资产或 USER 审核状态；维度分项尚未打分、\`score_status=ESTIMATED\`。

**DONE（本规则落地）**：现有 Q/Canvas/Linear 能引用本量尺并明确历史兼容、准入与证据边界。**STOP**：未经用户确认不冻结阈值、不批量迁移分数、不新建第二个问题系统、不据此变更 USER 两主任务或 Agent 并行策略。
