# B端 → 云端 Work｜H3 图像验证交接与澈 MV 风格基准 v1.0

> 用途：这是 B 端给 Work 的**验证说明书**，不是 B 端已完成图片验证的证明。每小时任务复制本文件的核验要求，另写一份 `tasks/inbox/<task_id>_WORK_VALIDATION.md`，与任务 JSON、H3 描述词一起提交。Work 自行核验、自行决定是否开始渲染；**无需把验证结果回传给聊天端**。B端不等待 Work 回写即可继续下一个小时的文本任务。

## A. 两端边界和状态

- B端：读取角色卡、真实13图池索引，编译十元动态链、镜头、描述词、参考图绑定说明；生成验证 MD 和文字任务并提交 GitHub。
- Work：按验证 MD 找到**真实原图字节**、把它们绑定 H3 对应 Picture 输入、检查角色身份和视图用途；通过后自行渲染。B端提供文件名/路径不是绑定成功的证据。
- 原图不在 GitHub（例如冒险者、鼠耳异变少女）：Work 在自己的可访问素材库定位，找不到则保持待验证状态；不得拿场景图、其他角色图或仅有的文字描述冒充原图。
- Work 验证失败时由 Work 自行排查素材错配、视图误用、H3 参数，再决定是否重跑；**不要求 B端等待或依赖 Work→ChatGPT 的验证消息**。
- B端写入 `queued_for_workbuddy_validation` / `pending_image_validation` 是**交接前状态**，不是“云端又失败了”的推断。除非 Work 留下可核实的记录，不写 passed、uploaded 或 rendered。

## C. 每轮 WORK_VALIDATION.md 必填项目

```yaml
task_id: "<对应的真实任务ID>"
character_id: "<三选一>"
identity_card_path: "<真实GitHub身份卡路径>"
reference_view_type: "full_body_identity | half_body_dynamic | both"
character_reference:
  full_body_identity: "<真实文件名及可访问位置；不存在则写 pending>"
  half_body_dynamic: "<真实文件名及可访问位置；不存在则写 pending>"
  github_image_upload: "true | false | unknown"
scene_reference:
  scene_id: "SCENE-XX"
  source_path: "<从GITHUB_13_SCENE_POOL_V1逐字读取>"
  github_blob_sha: "<索引中的值；缺失则写 null，不伪造>"
picture_mapping:
  picture_1: "角色动态主参考或现有唯一角色原图"
  picture_2: "第二身份视图（若有）或场景；必须同时在H3描述词标清"
  picture_3: "场景（仅当picture_2已用于第二身份视图）"
handoff_status: "queued_for_workbuddy_validation"
image_validation: "pending_image_validation"
render_claim_from_b_end: "not_rendered_by_b_end"
```

绑定完成前，Work 按顺序核查：
1. 角色 ID、身份卡与原图是否为**同一个人**；多视图是否同一角色，有无把四宫格当四个人。
2. Picture 顺序和 H3 正文 `<Subject 1>`、`<Picture 1>` 等引用是否一一对应；场景不可覆盖角色原型；缺图不能用文字占位假装绑定。
3. 视图类型是否正确：半身图锁脸/表情/识别件与上身动态；全身图锁比例/衣装/装备位置。只有全身图时优先低动作测试。
4. 场景源文件是否与 `scene_id/source_path` 一致，环境色彩与项目真实色卡不互相覆盖。
5. 预览或首尾帧是否出现换脸、变头发/耳形、长尾断接、装备消失、角色多生、服装漂移；若有，Work 按问题定位素材和参数，不先改正式角色卡。
6. 若原图可用且身份核验通过，Work 可以自行渲染；否则继续在 Work 侧排队/修复。是否提交视频和评分由 Work 自行决定，不构成 B 端下一小时任务的前置条件。

## D. 用户确认的澈 MV 案例：移植的是**生产方法和风格品质**，不是澈本人

用户确认此前 **澈 LLL-CHARM #4/#5** 的角色魅力 MV 表现最好，**包括画风**。两次使用同一份约10秒的 prompt；其历史文本在 Work 侧：
- `LLL-CHARM-20260921-104620`：`D:\H3\h3_workflow\incoming\hermes\20260921_104644_24012\task_0_prompt.md`
- `LLL-CHARM-20260921-114620`：`D:\H3\h3_workflow\incoming\hermes\20260921_114648_33612\task_0_prompt.md`
以上是用户提供的历史记录路径，**不代表 GitHub 中已有这两个文件或 B 端亲自看过渲染成片**。Work 若本机仍有历史 prompt/输出，可用实际成片作为风格 A/B 对照；不存在时以以下可执行特征为基准，不凭空捏造视频分析。

可迁移到各角色的核心方法：
- **明确的视觉优先级**：角色原图 fully_preserved；场景图仅做 environment/composition reference；辅助对象只当关系端点，不抢主体身份。
- **有辨识度的手绘感**：干净的二维轮廓、疏密可控的线条、局部轻薄晕染、柔和分层光、物体边缘的细致微动；避免碎线、无来由的爆光、塑料式体积光和频繁形变。依角色已有原稿画风与场景色卡微调，而非统一改造成澈的水彩能量人。
- **情绪通过动作而不是堆术语表现**：短暂停顿→精确小动作→环境或关系的可见变化→留给观众辨认的落点；character MV 不等于角色站桩，也不等于连续快切打斗。
- **镜头/音乐服务单一 changed_variable**：镜头远近、视角和运动有叙事任务，保留一次可读的构图转换；音乐有起伏与触发点，但不能为模仿而固定成澈的神圣慢板、竖琴铃声或四段切分。15秒一段控制2–4个清楚的镜头，具体由动作决定；两段之间保留空间、动作和音色连续性。
- **必须不复制的澈个人设计**：青白发与呆毛、灰紫脸、发光透明能量身体、能量丝、无衣装设定、神圣人格与原案关系对象；不得把鼠耳少女改成澈、把黎黎隆换成能量体，或把冒险者的装备抹除。
