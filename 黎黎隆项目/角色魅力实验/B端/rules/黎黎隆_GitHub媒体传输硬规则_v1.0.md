# 黎黎隆｜GitHub 媒体传输硬规则 v1.0

## 1. 总规则

从本规则生效起，GitHub Desktop 和所有自动提交任务：

> 不上传图片、视频或其他原始媒体，只提交图片的结构化文字描述、索引、任务和配置。

GitHub 是 B 端与 C 端之间的文字数据交换层，不是图片仓库、素材备份仓库或图片传输中转站。

## 2. 禁止提交

禁止提交以下原始媒体文件：

- PNG、JPG、JPEG、WEBP、GIF、BMP、TIFF、PSD
- MP4、MOV、AVI、MKV、WEBM
- 任何原图、视频、缩略图、截图或二进制媒体附件

也禁止：

- 为了让 B 端“看到图片”而复制图片进 GitHub
- 在 H3 描述词中伪造 GitHub 图片链接
- 把图片压缩、改名或转换格式后绕过规则提交

原图只保留在 A 端 / Obsidian 本地素材库和 C 端本地生产环境。

## 3. GitHub 允许提交

允许提交：

- 角色、场景、道具、参考图的 Markdown / YAML / JSON 结构化描述
- `asset_id`、原始文件名、本地相对路径、SHA-256、尺寸和版本信息
- 主体、构图、形体、色彩、风格、十元关系、动态链和镜头价值
- B 端生成的 H3 描述词、任务队列、状态、审核记录和失败原因
- C 端读取所需的字段约束和配置文件

## 4. 图片描述最低字段

每张进入 B 端任务的图片，必须先有文字记录：

```yaml
asset_id: LLL-CHAR-001
asset_type: character # character / scene / prop / reference
source_name: 原始文件名
source_path: 本地素材库相对路径
sha256: 原图哈希
semantic_description: 画面结构化描述
visual_language:
  silhouette: []
  proportion: []
  palette: []
  style: []
ten_yuan:
  main: ""
  secondary: ""
dynamic_chain: []
shot_value: []
status: verified
```

没有 `asset_id`、原图哈希或结构化描述时，B 端不得把素材投入正式 H3 任务，必须标记：

```text
blocked_missing_asset_description
```

## 5. 三端职责

- **A端**：保存原图，维护原图与 `asset_id` 的唯一对应关系。
- **B端**：只读取文字数据，完成语义理解、十元分析、动态链设计和 H3 描述词生成。
- **GitHub**：保存文字中间表示、索引、任务队列、版本和审核记录。
- **C端**：根据 `asset_id` 从本地素材库找到原图，执行实际生图或视频生产。

数据流固定为：

```text
本地原图
  ↓ asset_id + SHA-256
图片结构化文字描述
  ↓
十元关系 / 动态链
  ↓
H3 视频描述词
  ↓ asset_id
C端本地素材调用与生产
```

## 6. 每小时任务提交闸门

每小时任务在 Git commit / push 前必须：

1. 扫描本轮新增和修改文件。
2. 拒绝所有图片、视频和工程媒体文件。
3. 检查每个 H3 任务是否引用有效 `asset_id`。
4. 检查每个 `asset_id` 是否有对应文字描述和 SHA-256。
5. 检查输出是否只包含 Markdown / YAML / JSON / CSV / TXT 等文字数据。
6. 全部通过后才允许提交。

发现媒体文件时，任务必须失败并报告文件名，不得自动压缩、改名、转链接或强行提交。

## 7. B端任务固定输入与输出

### 输入

- 角色库文字描述
- 场景库文字描述
- 图片结构化语义描述
- 十元关系与动态链数据
- 音乐和镜头规则
- 有效的 `asset_id`

### 输出

- H3 视频描述词
- 镜头卡
- 动态链记录
- `asset_id` 依赖清单
- 任务状态和审核记录

B 端不直接传图片。C 端如果无法按 `asset_id` 找到本地原图，任务状态写为：

```text
waiting_for_local_asset
```

不得假装已完成生产。

## 8. 角色魅力 B端角色卡规范

### 8.1 规范名称

角色魅力 B端使用统一的 **H3角色素材化四宫格** 作为角色卡基础格式。

角色卡画布固定为 **9:16竖幅**。四个视图必须在同一张 9:16 画布内完成排布；不得改成横幅、改变四格顺序，或为了适应画面而裁掉身体与头部关键结构。

这张角色卡的作用不是做漂亮概念图，也不是重新设计角色，而是把一个角色拆成 H3 和动画生产能够稳定读取的四类固定信息：

- 身体比例
- 身体的空间关系
- 脸型与表情
- 头部转面与五官空间

### 8.2 四宫格固定布局

**画布比例：9:16（竖幅）**

四宫格采用 2×2 排布，四个区域共同占用整张竖幅角色卡：

```text
┌────────────────┬────────────────┐
│                │                │
│   全身比例稿   │   全身45°稿    │
│                │                │
│  不强调脸      │   保留结构     │
│  锁身体比例    │   锁空间关系   │
│                │                │
├────────────────┼────────────────┤
│                │                │
│   头部表情稿   │   头部45°稿    │
│                │                │
│  锁脸型       │   锁五官空间   │
│  锁帽子/角/耳 │   锁头部转面   │
│                │                │
└────────────────┴────────────────┘
```

| 位置 | 视图 | B端必须读取 | 不承担的任务 |
|---|---|---|---|
| 左上 | 全身比例稿 | 头身比、四肢比例、身体轮廓、服装主体、尾巴/附属结构的整体长度 | 不以脸部细节作为主要判断依据 |
| 右上 | 全身45°稿 | 身体厚度、前后关系、结构转折、附属物与身体的空间关系 | 不随意改变身体比例或结构连接 |
| 左下 | 头部表情稿 | 脸型、五官基本位置、表情范围、帽子/角/耳等头部识别件 | 不把表情稿当作全身比例依据 |
| 右下 | 头部45°稿 | 五官在转面后的空间位置、头部体积、侧面结构、帽子/角/耳的转面关系 | 不把正面五官平移到45°面而不做空间调整 |

### 8.3 角色卡锁定顺序

B端读取角色卡时，固定按照以下顺序建立角色身份锁：

```text
全身比例稿
  ↓ 锁身体比例与主体剪影
全身45°稿
  ↓ 锁身体厚度与空间关系
头部表情稿
  ↓ 锁脸型、表情与头部识别件
头部45°稿
  ↓ 锁五官空间与头部转面
角色魅力动态链 / 镜头设计 / H3描述词
```

角色卡的四个视图共同构成一个角色身份锁。缺少其中一格时，B端可以做素材审核和补全建议，但不得把该角色标记为“完整角色素材”并直接进入正式 H3 生产。

### 8.4 B端结构化记录字段

每张角色卡的文字索引应至少记录：

```yaml
card_type: h3_character_materialization_4grid
card_version: "1.0"
character_id: ""
canvas:
  aspect_ratio: "9:16"
  orientation: portrait
grid_assets:

  full_body_45:

    asset_id: ""

  head_45:
    asset_id: ""

identity_lock:
  proportion: []
  silhouette: []
  face_shape: []
  head_parts: []
  spatial_relation: []
status: verified # draft / incomplete / verified / rejected
```

### 8.5 进入角色魅力 B端任务的闸门

角色卡只有在以下内容通过后，才能被角色魅力 B端任务调用：

1. 四宫格位置完整，或明确标记缺失位置。
2. 四格均有有效 `asset_id`，并能关联本地原图和 SHA-256。
3. 角色卡画布比例为 9:16 竖幅，四格没有被错误裁切。
4. 身体比例、主体剪影、脸型、头部识别件已经写入文字索引。
5. B端任务明确本轮使用的视图：全身、全身45°、头部或头部45°。
6. H3描述词不得改变角色卡锁定的身份、比例、脸型和核心造型。

缺少关键视图时，任务状态写为：

```text
blocked_incomplete_h3_character_card
```

### 8.6 与角色魅力实验的关系

四宫格负责 **角色一致性和素材可用性**；十元关系、动态链和镜头语法负责 **角色魅力如何被表现**。

固定关系为：

```text
H3角色素材化四宫格
  ↓ 身份/比例/空间锁
角色十元关系
  ↓ 角色魅力的主次结构
动态链
  ↓ 变化与生克补过程
镜头语言与H3视频描述词
```

四宫格不能替代十元分析；十元分析也不能覆盖或改写四宫格锁定的角色基础结构。

## 9. 生效原则

十元用于创造和分析；视频描述词用于让模型看见；原图留在本地；GitHub 只保存图片的结构化文字描述、索引、任务和配置。
