# 土轴 n↔x并z｜生命周期：承载转移后公共接口可独立保持 v0.1

> L4 research-only。只补土轴生命周期与 SPLIT_ACTOR / SPLIT_OBJECT_LAYER 边界，不修改 L1/L2 canonical、十元信息卡、准度卡、正式关系卡或行为 evidence 正本。

## 1｜本轮唯一缺口

上一轮已经锁定：

```text
T0: n ON + x并z ON
-> 只撤公共接口
T1: n ON + x并z OFF
```

并留下反向缺口：

> 当原 actor 不再真实承载对象，但其公共壳仍稳定把第三方路由到当前真实内部对象/能力时，是否允许 `n OFF + x并z ON`？

本轮结论候选：**允许，但必须 SPLIT_ACTOR / SPLIT_OBJECT_LAYER，并证明公共壳仍有现实路由后果。**

新增判别门：

```text
CARRIER-INTERFACE-DECOUPLING-GATE-v0.1
```

## 2｜current criterion

### n

```text
n = object -> inside -> sustained load on carrier
```

要求当前 actor 自己持续承担对象带来的现实负荷：资源、维护、协调、风险、状态处理等。

若现实负荷已完整转移给另一 carrier，则对原 actor：

```text
n = OFF / FAIL
```

即使原 actor 仍拥有名称、入口、品牌、账号、客服或调度界面，也不能由这些外壳倒推出 `n`。

### x并z

```text
x并z = third_party -> public shell/interface -> identifiable/callable internal object
```

若原 actor 的公共壳仍满足：

```text
stable_public_shell_current = true
stable_mapping_current = true
third_party_repeatable_routing_current = true
routing_consequence_current = true
```

则允许原 actor 在“公共接口/代表/路由层”继续判：

```text
x并z = PASS
```

即便真正承担内部现实负荷的是另一 actor。

因此：

```text
n OFF
DOES NOT ENTAIL
x并z OFF
```

但前提是不能把历史壳、空品牌或死入口冒充为 current x并z。

## 3｜完整 IR：同一公共壳、承载者切换

结构化测试场景：某创作工作室最初自己接单并自己制作。后来工作室保留同一公开品牌、官网、项目提交入口、客户账号和统一交付窗口，但制作团队整体迁移到独立制作公司 B。客户仍只通过原工作室的公开接口提交项目、查看状态和领取交付；原工作室不再承担画师排班、渲染机器、素材生产、版本维护与制作事故修复，这些现实负荷全部由 B 承担。原工作室的接口仍把每个客户项目稳定路由到 B 的对应生产单，并将 B 的真实状态与交付结果映射回客户。

```yaml
actor:
  interface_actor: 原创作工作室A
  carrier_actor: 独立制作公司B
object: 同一批客户项目及其生产能力
object_layer:
  n_test: production_carrying_layer
  x并z_test: public_routing_representation_layer
current_window: T0_A自营制作 -> T1_B承载且A保留公共壳
changed_variable:
  carrying_actor: A -> B
  public_interface_owner: A -> A
  third_party_repeatable_routing: true -> true
relation_source:
  n_T0: A_internal_production
  n_T1_A: none
  n_T1_B: B_internal_production
  x并z_T0_A: A_public_shell_to_A_production
  x并z_T1_A: A_public_shell_to_current_B_production
relation_shape:
  n_T0_A: project -> A_inside -> sustained production load on A
  n_T1_A: no sustained production load on A
  n_T1_B: project -> B_inside -> sustained production load on B
  x并z_T1_A: third_party -> A_public_shell -> stable mapped callable B_internal_project_object
decision_right:
  A: controls public intake/routing/representation only
  B: controls production execution and internal handling
path_set:
  public_paths_held_by_A:
    - public_project_submission
    - client_account_status
    - unified_delivery_endpoint
    - public_support_ticket
  sustained_load_paths_T1:
    - artist_scheduling_by_B
    - render_capacity_by_B
    - asset_versioning_by_B
    - production_incident_repair_by_B
reentry_right:
  third_party: can repeatedly re-enter same project through A_public_shell
  project_internal_handling: occurs in B
future_endpoint:
  third_party: receives current project status/delivery through A shell
  carrying: remains borne by B unless transferred again
reality_anchor:
  - A入口提交的现实工单会生成/定位B的对应生产单，而非只留下营销线索
  - B的生产状态变化会通过A的同一公共接口回映给客户
  - A不再承担画师排班、渲染资源、生产维护与事故修复
  - B持续实际消耗资源并处理项目负荷
```

### 判定

```text
T0 / actor A:
  n PASS = 0.97
  x并z PASS = 0.97

T1 / actor A:
  n OFF/FAIL = 0.98
  x并z PASS = 0.96

T1 / actor B:
  n PASS = 0.98
  x并z on public layer = not entailed
```

关键纪律：T1 不得把 A 的 `x并z` 反推成 A 仍有 `n`；也不得把 B 的 `n` 自动反推成 B 拥有公共 `x并z`。

## 4｜nearest-neighbor 最小差异

固定：

```text
同一客户
同一项目
同一公开品牌
同一官网/账号/交付入口
同一第三方使用习惯
同一项目标识
```

只改变：

```text
who_bears_sustained_production_load
A -> B
```

### A｜自营阶段

A 的公开接口把客户送进 A 自己的制作系统，A 自己承担制作负荷。

```text
A: n PASS + x并z PASS
```

### B｜承载转移阶段

公共接口和稳定映射完全不变，但现实制作负荷全部转给 B；A 的入口仍可重复调用并真实路由到 B 的当前项目对象。

```text
A: n OFF + x并z PASS
B: n PASS
```

因此最小变化不是“有没有网站”，而是：

```text
carrier_identity changes
while
public_routing_identity remains stable
```

## 5｜Removal test

从 T1 只拿掉 A 的现实承载：

```text
artist_staffing
render_resources
asset_maintenance
production_incident_handling
```

保留：

```text
public_submission
stable_project_mapping
client_status_query
real_delivery_routing
```

若解释器因为 `n` 在 A 上关闭而自动关闭 `x并z`，则发生 carrier/interface conflation。

反过来，如果拿掉的是：

```text
stable_mapping
real routing to B
current status reflection
```

只留下品牌、官网和客服话术，则：

```text
A: x并z FAIL
```

即使“壳”视觉上仍存在。

## 6｜Reverse test

把制作负荷从 B 再迁回 A，公共壳保持不变：

```text
T1 A: n OFF + x并z ON
T2 A: n ON + x并z ON
```

恢复的是 A 的 sustained carrying，不是重新创造公共接口。

反方向再将公共接口关闭，但 B 继续制作：

```text
A: n OFF + x并z OFF
B: n PASS
```

说明 carrier 与 interface 是两个可独立变化的状态量。

## 7｜freeze-third-factor

冻结：

- 客户数量
- 项目类型
- 品牌名称
- 官网域名
- 账号系统
- 项目标识
- 交付标准
- 情绪/题材/职业称呼

只变：

```text
sustained_load_carrier = A -> B
```

如果 `x并z` 随承载者切换自动消失，说明错误地把“内部对象必须由壳所有者亲自承载”塞进了定义。

## 8｜positive / negative controls

### Positive control｜平台/系统域

一个 SaaS 门户保留固定域名、租户账号、API endpoint 和工单入口，但实际计算、数据库运行与故障恢复全部迁到独立云服务商 B。第三方仍通过原 SaaS 门户稳定调用同一业务能力，调用真实落到 B 的后端。

```text
portal_actor:
  n on compute-carrying layer = OFF
  x并z on public-callable layer = PASS

cloud_carrier_B:
  n = PASS
```

用于验证不是“创作外包”题材造成的特例。

### Negative control 1｜空品牌壳

A 保留官网、品牌和“提交项目”按钮，但按钮只进入无人处理邮箱，不能映射到 B 的任何当前生产对象。

```text
A: n OFF
A: x并z FAIL
```

### Negative control 2｜私人转介绍

A 不再有稳定公共入口，仅负责人偶尔私聊把熟客介绍给 B。

```text
A: x并z FAIL
```

因为这是偶发私人关系，不是第三方可持续识别/调用的公共壳。

### Negative control 3｜B 有承载但无公共壳

B 持续承担项目生产，但陌生客户无法识别、调用或直接进入 B，只能经 A 路由。

```text
B: n PASS
B: public x并z not entailed
```

这与 A 的 `n OFF + x并z PASS` 构成双向拆分。

## 9｜SPLIT_ACTOR / SPLIT_OBJECT_LAYER 纪律

当自然语言写：

> “A 平台承接项目并持续提供制作服务。”

不得直接给 A 同时贴 `n + x并z`。

必须先拆：

```text
IR-1 carrying:
object -> who actually bears recurring load?

IR-2 interface:
third_party -> which public shell -> which current callable object?
```

若答案是：

```text
carrying = B
public shell = A
```

则必须：

```text
SPLIT_ACTOR = true
SPLIT_OBJECT_LAYER = true
```

不得用公共品牌归属倒推现实承载归属。

## 10｜最小判别式

```text
n(actor_i) = sustained_load_dependency_borne_by(actor_i)

x并z(actor_i) = stable_public_shell_owned_or_operated_by(actor_i)
                AND stable_mapping_to_current_internal_object
                AND repeatable_third_party_routing
                AND real_routing_consequence
```

因此：

```text
carrier(actor_i) can become false
while
interface(actor_i) remains true
```

只要：

```text
public shell still routes to a real current object/carrier
```

而不是路由到历史残影、空壳或无人处理入口。

自然语言最短问法：

> “这个主体现在还亲自承担里面对象的持续现实负荷吗？如果不承担，外面的人是否仍能通过它的稳定公共壳，反复、真实地调用到当前正在工作的内部对象/能力？”

前问判 `n`，后问判 `x并z`，答案可以分别是“否 / 是”。

## 11｜新增 guard / failure types

```text
GUARD_EARTH_CARRIER_INTERFACE_01:
public_shell_owner != sustained_load_carrier
=> SPLIT_ACTOR before classification

GUARD_EARTH_CARRIER_INTERFACE_02:
carrier_transferred
AND stable_repeatable_real_routing_preserved
=> do not auto-off x并z on interface actor

GUARD_EARTH_CARRIER_INTERFACE_03:
brand_or_shell_present
AND real_mapping_or_routing_absent
=> x并z FAIL

FAILURE_PUBLIC_SHELL_AS_INTERNAL_CARRYING:
有平台/品牌/入口就倒推出壳所有者仍承担内部负荷

FAILURE_CARRIER_TRANSFER_AS_INTERFACE_DEATH:
承载转给别的 actor 就自动判公共接口死亡

FAILURE_OUTSOURCING_WORD_AS_N_OFF:
只看到“外包”一词就判 n OFF；必须证明现实持续负荷真的已转移

FAILURE_BRAND_RESIDUE_AS_X并Z:
品牌还在但接口不再真实路由，仍判 x并z

FAILURE_DOWNSTREAM_CARRIER_AS_PUBLIC_INTERFACE:
后端真实承载就自动给后端 x并z

FAILURE_SINGLE_ACTOR_COLLAPSE:
一句自然语言中的“平台提供服务”不拆接口 actor 与承载 actor
```

## 12｜本轮机制价值

土轴现在在案例层获得四种基本组合：

```text
n OFF + x并z OFF
n ON  + x并z OFF
n ON  + x并z ON
n OFF + x并z ON
```

最后一格只有在 carrier/interface 被正确拆分时才稳定成立。

这不改变 L1 的“外→内承载 ↔ 内→外映射外化”，反而提供案例层证据：两条反向箭头共享内外边界变量，但不互相逻辑蕴含。

## 13｜下一断点

四状态基本组合已经闭合，下一轮不应再重复寻找 `n OFF + x并z ON` 同型例子。

最高价值断点转为：

```text
进入 -> n承载 -> x并z外化
```

中的**方向反转最小门**：固定同一对象与同一 actor，测试何时“把外部对象接进来承担”真正转换为“把内部对象通过公共壳推出去供第三方调用”，并验证二者是否必须 SPLIT_IR，还是能在严格同一 object_layer 上形成可比的相反操作。

在该断点完成前不升级 canonical。
