# 土轴 n↔x并z｜稳定能力角色可外化，但轮换实例不自动外化：对象层级解析门 v0.1

> L4 research-only。只处理一个新执行边界：同一稳定公共接口可能长期指向“能力角色/服务类对象”，而内部具体实例持续轮换。此前 per-object resolver 已证明 opaque pool 中某个实例不能被自动判 x并z；本轮补齐相反边界：实例不可解析，不等于能力角色本身不可解析。

## 0｜本轮唯一缺口

既有土轴已经建立：

```text
stable public shell
+ causal grounding
+ object-specific resolver
=> object-level x并z candidate
```

以及：

```text
public shell -> opaque pool {S1,S2}
!= x并z(S1)
!= x并z(S2)
```

但这里还缺一个 object_layer：

```text
service_role / capability_class
```

例如：

```text
/search -> 当前任一可用 search replica
```

第三方无法要求下一次仍进入 `search-v1`，却可以持续识别、调用、归因到“搜索服务”这一稳定能力角色。

因此：

```text
instance_unresolvable
!= capability_role_unresolvable
```

同时也禁止：

```text
capability_role x并z PASS
=> each runtime instance x并z PASS
```

新增：

```text
EARTH-CAPABILITY-ROLE-AS-TESTED-OBJECT-GATE-v0.1
EARTH-NO-CAPABILITY-TO-INSTANCE-BACKFILL-v0.1
EARTH-OBJECT-LAYER-RESOLUTION-LEDGER-v0.1
```

## 4｜Removal

### Removal A｜删除稳定 capability contract

若 `/search` 每次可能代表完全不同能力，只有一个复用 URL：

```text
x并z(Search-Service): PASS -> FAIL / insufficient
```

说明 URL token 本身不是能力角色连续性的证据。

### Removal B｜删除实例稳定性

让 v1 每分钟销毁重建，但 `/search -> Search-Service` 合约保持：

```text
x并z(Search-Service): remains PASS
x并z(v1): remains insufficient
```

说明实例持续性不是能力层 x并z 的必要条件。

### Removal C｜删除第三方可调用性，只剩内部日志里叫 Search-Service

```text
x并z(Search-Service): PASS -> FAIL
```

说明“内部存在稳定角色”仍不能代替公共外化。

## 5｜Reverse



## 8｜失败类型

```text
FAILURE_INSTANCE_OPACITY_ERASES_CAPABILITY_XZ
```

含义：因为具体实例不可解析，错误否定稳定能力角色的 x并z。

```text
FAILURE_CAPABILITY_XZ_BACKFILLS_INSTANCE
```

含义：能力角色 x并z PASS 后，自动给全部轮换实例判 PASS。

```text
FAILURE_ROLE_NAME_AS_PUBLIC_OBJECT
```

含义：仅凭“客服/审核/支持”等角色名存在，就把内部角色当成公共外化对象。

```text
FAILURE_SHARED_URL_AS_STABLE_CAPABILITY
```

含义：URL/入口 token 不变，但其实际职责对象持续漂移，仍误判稳定 capability object。

```text
FAILURE_PARENT_SYSTEM_BACKFILL_FROM_CAPABILITY
```

含义：一个能力入口成立后，自动给整个 parent system 判 x并z。

## 9｜guards

```text
GUARD_EARTH_CAPABILITY_INSTANCE_01:
resolver 必须记录 target_object_layer；禁止只记录“resolvable=true”。
```

```text
GUARD_EARTH_CAPABILITY_INSTANCE_02:
若 stable public shell 解析到 capability/role，而非 runtime instance，则只允许对 capability/role 做 x并z 判定。
```

```text
GUARD_EARTH_CAPABILITY_INSTANCE_03:
capability-level PASS 不得向 sibling/instance/parent 自动广播。
```

```text
GUARD_EARTH_CAPABILITY_INSTANCE_04:
实例轮换不自动破坏 capability-level x并z；但必须证明稳定职责/接口契约和真实第三方调用链。
```

建议 ledger：

```yaml
resolution_ledger:
  - tested_object_id: Search-Service
    object_layer: stable_functional_role
    shell: /search
    resolver_target_layer: capability_role
    causal_grounding: true
    third_party_repeatable_access: true
    verdict: x并z_pass

  - tested_object_id: search-v1
    object_layer: runtime_instance
    shell: /search
    resolver_target_layer: capability_role_not_instance
    third_party_repeatable_same_instance_access: false
    verdict: x并z_insufficient
```

## 10｜最小判别式

```text
IF
public shell is stable
AND shell causally enters the internal system
AND third party repeatedly invokes the same functional role/capability
AND role contract / responsibility remains stable
BUT runtime instances rotate opaquely

THEN
x并z(capability_role) = PASS candidate
x并z(runtime_instance) = insufficient
```

反面：

```text
IF
only the interface token is stable
BUT functional target / responsibility / contract drifts

THEN
stable capability-role x并z = insufficient
```

一句话：

> 可持续调用“这个能力”，不等于可持续调用“这个实例”；但实例轮换，也不等于这个能力没有稳定公共壳。

## 11｜与旧研究边界

本轮不是重复 per-object resolver ledger：

- 旧卡解决 `S1可解析、S2不可解析` 时不得 sibling broadcast；
- 本轮解决 `能力角色可解析、具体运行实例不可解析` 时，两者属于不同 object layer，必须允许同时得到不同判定。

本轮也不是重复 object-anchor-before-axis：

- object anchor 卡解决自然语言先绑错对象；
- 本轮解决对象已经绑对后，`role/class` 与 `instance` 两层都真实存在，resolver 到底落在哪一层。

因此本轮新增的是：

```text
object identity
+
object layer of resolver target
```

而不是新增 canonical criterion。
