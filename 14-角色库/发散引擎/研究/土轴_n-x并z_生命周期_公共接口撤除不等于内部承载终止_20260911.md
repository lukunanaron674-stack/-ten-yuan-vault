# 土轴 n↔x并z｜生命周期：公共接口撤除不等于内部承载终止 v0.1

> L4 研究层。只测试 `n↔x并z` 生命周期中的状态解耦，不修改 L1/L2 canonical、十元信息卡、准度卡、正式关系卡或行为 evidence 正本。

## 1｜本轮最小缺口

已有两道候选门：

```text
n = object -> inside -> sustained load on carrier
x并z = third_party -> public shell/interface -> identifiable/callable internal object
```

并分别补出：

```text
对象进入内部 ≠ n
公共壳存在 ≠ x并z
```

但静态双向负控还不能证明生命周期中两端真的可独立变化。

本轮只问一个最小问题：

> 当同一 actor、同一 object、同一内部承载层保持不变，仅撤除第三方公共接口时，`x并z OFF` 是否必然推出 `n OFF`？

结论候选：**不推出。**

新增判别门：

```text
PUBLIC-INTERFACE-OFF-vs-CARRYING-PERSISTENCE-v0.1
```

## 2｜current criterion

若在 `T0 -> T1` 中满足：

```text
sustained_load_dependency remains true
carrier continues recurring handling
object remains internally maintained
```

同时：

```text
stable_public_shell becomes unavailable
third_party_repeatable_routing = false
public attribution / entry / call path = off
```

则允许：

```text
T0: n PASS + x并z PASS
T1: n PASS + x并z FAIL/OFF
```

禁止解释器做：

```text
x并z OFF => n OFF
```

也禁止反过来把“内部还在运行”当成公共接口仍然存在。

## 3｜完整 IR：同一对象生命周期

输入：

> 某社区康复中心在 T0 同时具备两件事：内部长期承载 20 名住民，持续提供床位、饮食、用药、夜间值守、康复排程和事故处置；外部则有公开名称、地址、电话与线上申请入口，陌生家庭可以反复通过这些接口申请入住、查询和进入接待流程。T1 因安全事件进入封闭运行：公开电话停接新申请、官网入口下线、门牌仍保留但不再提供外部进入与申请；然而原 20 名住民仍继续由同一中心承担床位、饮食、用药、夜间值守、康复排程和事故处置，内部负荷没有外包，也没有中止。

```yaml
actor: 社区康复中心
object: 已入住的20名住民及其持续照护关系
object_layer: internal_carrying_and_public_access_split
current_window: T0公开接收+内部承载 -> T1封闭运行+继续内部承载
changed_variable:
  n_side: sustained_load_dependency = unchanged_true
  x并z_side: third_party_repeatable_routing = true_to_false
relation_source:
  n: internal_carrier
  x并z: stable_public_shell_then_withdrawn
relation_shape:
  n: object_inside_and_continues_depending_on_carrier
  x并z: third_party_routes_through_public_shell_to_internal_service_then_route_removed

decision_right: center_can_close_external_admission_but_still_bears_internal_care_duties
path_set:
  internal_carrying:
    - bed
    - food
    - medication
    - night_shift
    - rehabilitation_schedule
    - incident_handling
  public_interface_T0:
    - public_phone
    - online_application
    - public_address_entry
  public_interface_T1: []
reentry_right:
  existing_residents: remains_inside_under_current_carrying
  new_third_parties: public_entry_right_removed
future_endpoint:
  residents: continue_internal_care_or_later_exit
  strangers: cannot_currently_enter_through_public_shell
reality_anchor:
  - T1后连续排班、药物记录、床位占用和事故处置仍由同一中心发生
  - T1后公开申请与外部进入路径真实停止，而非仅改名
```

### 判定

```text
T0:
  n PASS = 0.98
  x并z PASS = 0.97

T1:
  n PASS = 0.98
  x并z FAIL/OFF = 0.96
```

这里必须 SPLIT_IR。`x并z` 的 off 发生在“第三方公共调用/进入层”；`n` 的 pass 发生在“既有对象持续内部承载层”。

## 4｜nearest-neighbor 最小差异对

固定以下全部不变：

```text
actor
object
object_layer for internal carrying
resident count
bed / food / medication / staffing / risk handling
physical building
internal team
```

只改变：

```text
third_party_repeatable_routing
```

### A｜T0：接口存在

陌生家庭可通过公开电话、线上申请、公开接待入口持续进入同一中心流程。

```text
n = PASS
x并z = PASS
```

### B｜T1：接口撤除

停止公开申请、停接新入住、关闭线上入口；但既有住民照护负荷完全继续由中心承担。

```text
n = PASS
x并z = FAIL/OFF
```

**最小变化只在公共映射/路由，不在内部持续承载。**

因此：

```text
x并z OFF != n OFF
```

## 5｜Removal test

从 T0 只拿掉：

```text
public_phone
online_application
public_entry_for_new_third_parties
```

不拿掉：

```text
bed
food
medication
maintenance
staffing
coordination
risk_bearing
```

若解释器因为公共接口消失而同时把 `n` 判 OFF，则发生端点耦合误判。

## 6｜Reverse test

从 T1 反向恢复公共入口：

```text
公开电话恢复
线上申请恢复
陌生第三方再次能稳定进入同一接待流程
```

内部承载在 T1 与 T2 之间保持不变。

则：

```text
T1: n PASS + x并z OFF
T2: n PASS + x并z PASS
```

恢复的是 `x并z`，不是重新“制造” `n`。

## 7｜freeze-third-factor

固定：

- 机构名称
- 建筑位置
- 内部人员
- 住民对象
- 照护强度
- 资源消耗
- 风险承担
- 题材和情绪

只变：

```text
public_shell_current_usability
third_party_repeatable_routing
```

若 `n` 判定随官网/热线开关一起变化，而内部负荷从未改变，说明解释器把两条因果箭头混成了一条。

## 8｜positive / negative controls

### Positive control A｜工程系统：n 保持，x并z OFF

内部计算集群持续为既有生产任务供电、散热、调度、监控和故障恢复，但公网 API 被下线，只允许内部作业继续运行。

```text
内部任务继续依赖集群持续处理 -> n PASS
外部客户端无法再通过公共 endpoint 调用 -> x并z OFF
```

这证明该状态解耦不依赖“照护机构”题材。

### Negative control A｜两端同时 OFF

康复中心关闭后，公开入口停用，同时住民全部转出、值守撤销、用药与床位负荷终止。

```text
n OFF
x并z OFF
```

用于防止把“接口关闭后内部可能仍在”误扩张成“接口关闭时内部一定仍在”。

### Negative control B｜只有壳还在，但内部承载已 OFF

中心停业后官网、门牌、电话自动语音仍在，但住民全部离开，内部不再承担任何照护；电话也不能完成真实申请或进入。

```text
n OFF
x并z FAIL/OFF
```

用于防止把历史壳、纪念壳或自动回复误判为 current x并z。

## 9｜外→内 / 内→外方向纪律

本轮再次确认两条箭头必须分别读：

```text
n:
object -> inside -> sustained load on carrier

x并z:
third_party -> public shell/interface -> identifiable/callable internal object
```

生命周期中，一条箭头可以保持，另一条可以关闭。

这不是说两端“毫无关系”，而是说：

```text
它们是同一内外边界变量的相反方向操作，
但案例层状态不能互相逻辑蕴含。
```

## 10｜新增 guard / failure types

```text
GUARD_EARTH_LIFECYCLE_01:
public_interface_off
AND sustained_load_dependency_still_true
=> keep n independently evaluable; do not auto-off n

GUARD_EARTH_LIFECYCLE_02:
internal_carrying_continues
AND third_party_repeatable_routing_false
=> x并z current FAIL/OFF remains valid

FAILURE_COUPLED_ENDPOINT_SHUTDOWN:
x并z关闭就自动关闭n

FAILURE_INTERNAL_ACTIVITY_AS_PUBLIC_INTERFACE:
内部仍运行就倒推出x并z仍在线

FAILURE_SHARED_BUILDING_AS_SHARED_STATE:
因为两端发生在同一建筑/机构就拒绝SPLIT_IR

FAILURE_HISTORICAL_SHELL_AS_CURRENT_X并Z:
接口过去存在但当前不可调用，仍判x并z PASS
```

## 11｜最小判别式

```text
n_current = sustained_load_dependency_current
x并z_current = stable_public_shell_current
              AND stable_mapping_current
              AND third_party_repeatable_routing_current

therefore:
x并z_current = 0
DOES NOT ENTAIL
n_current = 0
```

自然语言最短问法：

> “外面的人现在进不来了以后，里面原有对象还需不需要这个主体继续真实承担资源、维护、协调和风险？”

若答案是“仍然需要”，则 `n` 必须独立继续评估，而不是随 `x并z` 一起关掉。

## 12｜本轮结论与下一断点

本轮新增机制成立于 L4 candidate：

```text
T0: n ON + x并z ON
-> 只撤公共接口
T1: n ON + x并z OFF
```

这把此前静态“双向负控”推进成了真实生命周期状态迁移。

下一最小断点不再重复“接口撤除”案例，优先测试反方向：

```text
n OFF + x并z 是否还能短期保持 PASS？
```

重点区分：

1. 公共壳仍稳定把第三方路由到“当前真实内部对象”时，是否可能内部承载已经转移到别的 actor；
2. 若原 actor 仅保留品牌/入口、所有现实负荷已外包，`x并z` 是否仍可在原 actor 上成立，成立的 object_layer 应写成“路由/代表”而非“承载”；
3. `n OFF -> x并z ON` 是否要求 SPLIT_ACTOR / SPLIT_OBJECT_LAYER，避免把平台壳和实际承载者混为同一主体。

在该断点完成前，不升级 canonical。
