## 1. 问题摘要

用户在使用 `十元 F12 总控 v0.4-lite｜本体类创作` 时发现：

1. 脚本仍然没有真正等待回复完成，就进入下一轮。
2. 控制台日志显示：发送某轮后，几乎立刻检测到 `TASK_DONE:R?/30`。
3. 这说明脚本不是在读“最新 assistant 回复”，而是在错误范围内扫描到了标记。

核心判断：

> 问题不是“等待时间不够长”，而是“等待对象错了”。

---

## 2. 根本原因

旧版 `waitForTaskDone()` 使用类似逻辑：

```js
const body = document.body.innerText;
if (body.includes(marker)) {
  // 判定本轮完成
}
```

这会导致确定性误判。

原因：每一轮发送给 ChatGPT 的用户 prompt 本身就包含：

```text
结尾必须输出：TASK_DONE:R3/30
```

因此，当用户消息刚进入页面 DOM，`document.body.innerText` 已经包含目标 marker。脚本会把“用户消息里的要求”误判成“assistant 已经完成回复”。

截图中的连续日志：

```text
已点击发送按钮
等待回复完成：TASK_DONE:R7/30
检测到 TASK_DONE:R7/30
进入下一轮断点：8/30
```

与这个机制完全吻合。

---

## 3. 风险类型

### 3.1 用户 prompt 自带 marker

最高风险。每轮 prompt 都写着 `结尾必须输出 TASK_DONE`，全页扫描必然会撞到。

### 3.2 历史回复残留 marker

历史 R3 已完成后，页面里会永久残留 `TASK_DONE:R3/30`。重跑或切轮时，全页扫描也可能误判。

### 3.3 面板日志污染

F12 面板自己的日志里也会写：

```text
等待回复完成：TASK_DONE:R3/30
```

如果扫描范围包括面板文本，会再次污染判断。

### 3.4 导出文本 / 断点文本污染

如果页面上存在导出断点、日志、任务全文预览，也可能包含 marker。

### 3.5 流式输出提前 marker

即使 marker 真的是 assistant 输出的，也可能出现在正文中间。若一看到 marker 就立刻进入下一轮，仍可能抢跑。

---

## 4. 修复原则

### 原则一：禁止全页扫描

不能再用：

```js
document.body.innerText.includes(marker)
```

作为完成条件。

### 原则二：只读“本轮发送后新增的 assistant 增量文本”

发送前记录 assistant 基线：

- assistant 消息数量
- 最后一条 assistant 文本
- article 数量 fallback
- 当前 marker
- sentAt 时间

发送后只比较新增 assistant 内容。

### 原则三：marker 不是唯一完成条件

严格模式下完成条件应为：

```text
assistant 增量文本出现 marker
+
stop 按钮消失 / send 按钮恢复
+
quiet window 静默窗口通过
```

推荐 quiet window：1500ms-3000ms。

### 原则四：必须有 runId / abort

自动续跑期间若用户点击停止、上一轮、下一轮、重置，旧 wait loop 必须被终止。

需要：

- runId
- AbortController
- MutationObserver.disconnect()
- clearInterval / clearTimeout

### 原则五：localStorage 只存断点，不管实时竞态

`localStorage` 可保存：

- 当前 index
- 任务文本
- strict 开关
- 日志尾部

不应承担同页面实时协商。实时运行状态应在内存里维护。

---

## 5. 推荐完成检测算法

```text
发送前：
1. 解析当前 task 的 TASK_DONE:R#/N。
2. 记录 assistant 基线。
3. 创建 runId。
4. 创建 AbortController。

发送后：
1. MutationObserver 监听 main / article DOM 变化。
2. 每隔 pollMs 检查一次 assistant 增量文本。
3. 若增量文本出现 marker，记录 sawMarkerAt。
4. 不立刻完成，继续等待 UI idle。
5. 若 send 可用、stop 消失、quiet window 达标，则完成本轮。
6. index + 1。
7. 清理 observer / timer / abort handle。

失败：
1. timeout 无 marker → 停止。
2. runId 改变 → 停止旧 loop。
3. 用户 STOP → abort。
```

## 6. 伪代码

```js
function takeReplyBaseline(marker) {
  const assistants = getAssistantMessageNodes(true);
  return {
    marker,
    assistantCount: assistants.length,
    lastAssistantText: assistants.length
      ? textOf(assistants[assistants.length - 1])
      : "",
    ts: Date.now()
  };
}

function getAssistantDeltaTextSince(baseline) {
  const assistants = getAssistantMessageNodes(true);
  const texts = assistants.map(textOf);

  if (texts.length > baseline.assistantCount) {
    return texts.slice(baseline.assistantCount).join("\n\n");
  }

  const last = texts[texts.length - 1] || "";
  if (last.startsWith(baseline.lastAssistantText)) {
    return last.slice(baseline.lastAssistantText.length);
  }

  return "";
}

async function waitForTaskDone(ctx) {
  let sawMarkerAt = 0;
  let lastMutationAt = Date.now();

  const observer = new MutationObserver(() => {
    lastMutationAt = Date.now();
  });

  observer.observe(document.querySelector("main") || document.body, {
    subtree: true,
    childList: true,
    characterData: true
  });

  while (!timeout) {
    const delta = getAssistantDeltaTextSince(ctx.baseline);
    const idle = findSendButton() && !findStopButton();
    const quiet = Date.now() - lastMutationAt >= ctx.settleMs;

    if (!sawMarkerAt && delta.includes(ctx.marker)) {
      sawMarkerAt = Date.now();
    }

    if (sawMarkerAt && idle && quiet) {
      observer.disconnect();
      return true;
    }
  }

  observer.disconnect();
  return false;
}
```

## 7. 结构化日志规范

旧日志：

```text
检测到 TASK_DONE:R3/30
```

不够审稿。

新日志应使用事件型：

```text
PREPARE_SEND | round=3/30 marker=TASK_DONE:R3/30
SEND_CLICKED | round=3/30 marker=TASK_DONE:R3/30
WAITING | round=3/30 marker=TASK_DONE:R3/30 strict=true
GENERATION_STARTED | round=3/30
MARKER_SEEN | round=3/30 marker=TASK_DONE:R3/30
ROUND_DONE | reason=marker+idle+settled
ROUND_ADVANCE | next=4/30
```

危险日志模式：

```text
SEND_CLICKED
MARKER_SEEN
ROUND_ADVANCE
```

若三者同秒出现，通常表示仍在误判。

## 8. 严格模式与宽松模式

### 严格模式

默认。

必须满足：

```text
assistant delta 中出现 marker
+
UI idle
+
settled quiet window
```

否则 timeout 停止。

### 宽松模式

不自动越过。

若无 marker 但 UI idle，可弹窗：

```text
未检测到 TASK_DONE:R?/N。
是否手动确认本轮完成并进入下一轮？
```

宽松模式必须人工确认，不能静默自动跳。

## 9. 测试清单

| 场景 | 预期 |
|---|---|
| 用户 prompt 中包含 TASK_DONE | 不应触发完成 |
| 历史回复中已有同 marker | 不应触发完成 |
| 面板日志中包含 marker | 不应触发完成 |
| assistant 正文中间提前出现 marker | 等 idle + quiet 后才完成 |
| assistant 没有输出 marker | 严格模式 timeout 停止 |
| 点击 STOP | 当前 wait loop abort |
| 点上一轮 / 下一轮 | 旧 runId 失效，不再偷偷推进 |
| 重载页面后继续 | localStorage 恢复 index 与任务文本 |

## 11. 本轮经验金句

> 自动续跑不能问“页面里有没有 TASK_DONE”，必须问“本轮 assistant 新回复里有没有 TASK_DONE”。

> marker 是回执，不是咒语；写在 prompt 里的 marker 不能算完成。

> F12 总控的完成条件不是文字出现，而是：来源正确、状态回落、静默通过。

> localStorage 管断点，runId 管活的任务。
